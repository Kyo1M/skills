# analysis-plan — 分析計画

分析を始める前に、何のために・何を・どの順で見るかを決め、計画 md に残す。仮説の一覧から始めない。先に目的と指標を決め、指標の現状を見てから、確かめる仮説を目的ごとに置く。

notebook を作って問いに答えるのは `analysis-notebook`、レポートにするのは `analysis-report`。前提そのものを疑う深掘りや、構想がまだ固まっていない段階の論点整理は、先に `grill-me` を使う。

```
（必要なら grill-me）→ analysis-plan（計画）→ analysis-plan（分析設計 → レビュー → 合意）→ analysis-notebook（データを見て設計を直しながら）→ analysis-report（設計の目次から）→ docx-export
```

分析は必ず設計してから入る。計画（プロジェクト全体の目的・指標・仮説）があっても、1 回の分析ごとに分析設計 md を作り、依頼者と合意してから notebook を作る。3 つの skill に共通する考え方は `references/analysis-principles.md` にまとめてあり、最初に読む。

## 使い方

```
/analysis-plan [分析のテーマ / 既存の計画 md・仮説一覧のパス]
```

## 入力のモード

- **新規作成**: テーマと材料から計画 md を作る
- **作り直し**: 既存の仮説一覧・計画を読み、この型に組み直す。既存の仮説は捨てずに「これまでの仮説との対応」で行き先を示す
- **分析設計**: 1 回の分析（1 本のレポート・1 回の共有）の設計 md を作る。計画のどの段の、どの範囲をやるかを決め、レポートの目次まで置く（Step 2B）
- **更新**: 現状把握や仮説検証の結果を受けて、計画の優先度・仮説・取りに行くデータを直す（結果そのものは notebook とレポートが正本で、計画には行き先と状態だけを書く）

## Step 0: 規約を読む（最初に必ず実行）

`references/analysis-principles.md`（分析の考え方）を読む。続けて、ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイドを読み、次を決める。規約に明示があれば従い、無ければ既定を使う。

| 項目 | 既定（規約に無いとき） |
|---|---|
| 計画 md の置き場・名前 | `docs/analysis-plans/YYYYMMDD_<slug>.md` |
| 分析設計 md の置き場・名前 | 計画 md と同じ置き場で `YYYYMMDD_<slug>-design.md`。規約に分析計画の置き場があれば、そこに置く |
| frontmatter | 無し。規約に型があれば従う（種別は既存のものに乗せ、新しく増やさない） |
| テーブル定義・データの一覧 | 規約が指す場所（例: `docs/tables/`）を読み、指標の「データ」「期間」を埋める。無ければユーザーに聞く |
| 既存の指標の設計（スコア・KPI の定義書） | 規約・wiki が指す資料。原本が手元だけにあるときは、指標名と定義だけを使い、資料中のサンプル値・分布は写さない |
| 計画 md に書いてよい値 | 計画 md は notebook の外。個人の値・ID・個人の行・自由記述の原文は書かない。集計した件数（店舗数など）は規約が許す範囲で、確かめた日を添える |
| 実名の扱い | 規約に従う。決まりが無ければ、店舗・取引先などの実名を計画 md の例に出さない |
| 検査のコマンド・git の運用 | 規約に従う。無ければコミットしない |

## Step 1: 材料を集める

コードやドキュメントで分かることは自分で読む。ユーザーに聞くのは、決めないと計画が書けないことだけにする。

- 前提：プロジェクトの目的、結果を受け取る人と場（報告会・定例）、期限
- 判断する人と、その人がいま迷っていること（議事録・メモから拾う）
- 既存の指標の設計（スコア・KPI の項目・定義・平滑化や欠けの扱い）
- データの有無・粒度・期間・欠け（テーブル定義、データの確認メモ）
- これまでの分析・仮説と、その結果（重ねない・置き換えるため）
- 依頼者が話した比べ方・切り口

材料が足りずに目的が置けないとき（誰の判断か分からないなど）は、1 問ずつ聞く。聞くときは自分の案を添える。

## Step 2: 計画を 4 段で組む（固定）

雛形は `references/plan-template.md`。順番を入れ替えない。

### 2-1. 目的

- 誰のどの判断に使うかで置く。「区分」ではなく「目的」と呼ぶ。2〜4 個
- 列：目的／判断する人／結果で変わること
- 目的の間の依存を書く（例：指標そのものが状態を映しているかの確認は、その指標で対象を選ぶ他の目的の土台になる）
- 結果を受け取る場（報告会など）で、何が言えたかとして読まれるかを 1〜2 行で添える
- 判断する人がすでに持っている見立て（例：人への投資が店の改善・売上につながる）は、分析者が懐疑的でも目的か仮説に載せ、検出できる設計で確かめる。経営層向けの示唆を求められているなら、業績（KGI）とのつながりを見る目的を置く

目的のチェック:

- 手段が目的になっていないか（「相関を見る」「可視化する」は目的ではない）
- 結果で変わることが、判断する人の行動として書けているか
- 依頼の範囲（対象外にした判断）に踏み込んでいないか

### 2-2. 指標の一覧

- 目的と既存のスコア・KPI で使う指標に絞る。網羅のために指標を増やさない
- 列：カテゴリ／指標／定義（分子・分母・単位）／データ／期間／既存のスコアとの対応／目的
- 定義は既存のスコア・KPI の書き方に合わせる。値が手に入るなら（スコアの元の値など）、自分で計算した値と突き合わせて定義をそろえる、と書く
- 定義が割れる指標（離職率の対象範囲と分母、残業の閾値など）は、初期値を置き、決め方を表の下に書く。これを現状把握の最初の作業にする
- 期間と欠け（無い月・時点）を書く。期間が足りない指標は、使う目的を限る
- 比率の指標（予算達成率・前年比など）は、分母の決め方（予算の組み方、年度の切り替え）を確かめることにする。分母が対象の水準を割り落とすので、比率と並べて水準の指標（売上そのもの・席あたり売上など）も置く

### 2-3. 現状把握

指標ごとに、次の 4 つを見る。目的ごとには作らない（複数の目的で使う指標の図を作り直さないため）。

| 見ること | 中身 | 図の例 |
|---|---|---|
| 概要 | 最新の時点の対象間のばらつき、グループごとの違い、欠けている対象 | 箱ひげ図、ヒストグラム |
| 具体例 | 典型的な対象と、上位・下位の帯の対象で値がどう並ぶか | 表 |
| 推移 | 全体・グループの時点ごとの推移、季節の動き、欠けた時点 | 折れ線 |
| 指標どうしの関係 | 2 つの指標の関係を、規模・種類などの条件で分けて見る | 色分けした散布図、相関の表 |

決まり:

- 4 つを見る前に、対象の基本情報（グループごとの数・種類・規模・水準）を表にし、指標ごとに値の種類（数値か区分か）と範囲（区分なら値の一覧）を押さえる（`references/analysis-principles.md` の 4・5）
- 合成値（総合点・平均点）は、構成する項目までブレークダウンして見る（同 6）
- ここでは関係の有無の結論を出さない。全体をまとめた散布図は、規模などの条件の違いを見ているだけになりやすい。条件で分けて見せ、「関係がある・ない」は仮説検証で条件をそろえてから言う
- 優先する指標の順を決める（既存のスコアの中心の指標と、仮説検証で最初に使う指標から）
- 範囲を決める。指標は一覧に載せたものだけ、見ることは 4 つだけ、期限（初回の共有など）を書く
- 具体例は選ぶ規則で書く（例：中央値に最も近い対象）。個人の行・実名は notebook の中だけで見て、外に出すときは「典型的な対象」「上位の帯」に直す
- 欠けた時点・対象は推移の図にそのまま出す。データの持ち主に確かめるときは、この図と一緒に聞く
- 現状把握で答えの大部分が出る仮説（スコアの内訳など）は、その旨を書く
- 要約の値（中央値など）で評価する前に、グループ・対象ごとの内訳を見る
- 複数のグループが同じ月にそろって動くなら、共通の動き（季節・暦・予算の置き方）を疑い、全体のその月の値を引いた版も見る
- 割合が高い指標（定着率 8 割など）は、低い側（辞めた 2 割）に共通点があるかを、差が出る単位（店か人か）で見る
- 既存の合成スコアを相手が使い続ける前提なら、現状把握からロジックへの示唆を出す観点を入れる

| 観点 | 見ること |
|---|---|
| 重みと実際の効き方 | 設計上の重みと、店の差・月の動きのうちそのカテゴリで説明できる割合を並べる |
| 頭打ち・張り付き | 上限・満点に張り付く対象の割合。張り付くと差を表さない |
| 欠けの扱い | 点の無い対象・時点で、残りのカテゴリの重みが変わり、対象によって総合点の中身が違わないか |
| 重複 | 同じカテゴリ・カテゴリ間で相関の高い指標が、同じことを二重に数えていないか |
| 反映の遅れ | 実施・受け取り・反映の時差で、何か月前の状態を表しているか |
| 材料に使っていない指標との関係 | スコアの外の指標と予想外の関係が出れば、足す材料の候補になる |

### 2-4. 仮説検証

目的ごとに、仮説・検証方法・結果で変わることを組にする。

- 列：#／仮説／検証方法（種類：中身）／当たったら／外れたら／優先度（高・中・低）
- 検証方法は 4 種類のどれか（組み合わせてよい）

| 検証方法 | 中身 |
|---|---|
| 図で足りる | 分布や内訳を図にすれば答えが出る |
| 条件をそろえて比べる | 規模・種類などをそろえ、2 つ以上の群の差が偶然の幅を超えるかを見る |
| 前後を追う | ある出来事の前後で、指標がどう動くかを見る |
| 見込みを作る | 対象の条件から値の見込みを作り、実績との差を見る |

- 「当たったら」「外れたら」は、判断する人の行動で書く。外れても次の手が残る書き方にする（外れたら別の仮説・別の目的に回す、など）
- 優先度は、判断への効き方・データの厚さ・期限に間に合うかで仮に付け、付け方を書く。時期では書かない
- 表の下の補足に、仮説ごとの注意（欠けた期間の使い方、後から書き足されたデータで当たりが多く見える恐れ、少数の対象で見込みを作るときの条件の絞り方など）を置く

仮説のチェック（1 つずつ）:

- 反証できるか（どんな結果なら外れと言えるかを先に言えるか）
- 比べるときに何をそろえるか（規模・種類・時期）。そろえないと差が条件の違いで説明できてしまわないか
- 結果と原因に同じ材料が入っていないか（スコアの材料に業績が入っているのに、スコアと業績を比べる、など）
- データの期間・件数で足りるか。足りなければ「データ次第」と書き、取りに行くデータに回す
- これまでの分析と重ならないか。重なるなら置き換える理由を書く
- 相関から因果を断定する書き方になっていないか
- その設計で関係を検出できるか。対象ごとの平均を並べた相関だけでは、時差のある関係（人が減った翌月に売上が落ちる）や、比率が割り落とした水準の差は見えない。同じ対象の中の変化を時差つきで追う、条件の似た対象どうしで比べる、のどちらかを入れる

### 2-5. 計画の締め

- **これまでの仮説との対応**：既存の仮説一覧の各行が、この計画のどこに行ったか（置き換え・後に回す・現状把握で見る）
- **取りに行くデータ**：確かめられない仮説や、確かめ方が粗くなる仮説に要るデータと、効く仮説の番号
- **確かめること**：判断する人・依頼者にしか答えられないこと（目的の置き方、優先する目的、結果の出し方）。その場で答えが返る問いだけを置く

## Step 2B: 分析設計（1 回の分析ごと）

雛形は `references/design-template.md`。計画が無い小さな分析でも、この設計は作る。

- 目的は 2〜3 個。列は「目的／想定アウトプット」。基礎分析（分析者自身がデータを把握するための現状把握）では「判断する人」「結果で変わること」の列を置かない（`analysis-principles.md` の 10）。仮説検証の回は計画の書き方（判断する人・当たったら・外れたら）に従う
- 現状把握の回は、要素の前に対象の基本情報の表を置く（同 4）。要素ごとに、値の種類・範囲・内訳・全体と推移・取得状況を見る（同 5）。合成値は項目までブレークダウンし、項目のデータが無ければ確認事項にする（同 6）
- 依頼者が「深く知りたい」と言った要素は、「知りたいこと／見方／限界」の表に 1 行ずつ置く。目立つ偏りには業務上の素直な説明を置き、それを確かめる属性を書く（同 7）
- 既存のスコア・ロジックを扱う回は、点検の観点と、組み直しの候補の両方を置く（同 8）
- データの制約（欠損、集計済みで個人の行が無い、一部の人だけのデータ）は、分析の途中で気づくのでなく、設計の段階で書く。手元で母数を突き合わせられるもの（一部の人だけのデータか）は、設計を書く前に集計で確かめる
- notebook の分け方、日ごとの期限、時間が足りないときに落とすもの（行き先も）を書く
- レポートの目次（章番号つき）を置く。分析は、この目次を埋める方向に進める
- 使い回す素材（既存の notebook・図）は作業用の節に書く。リード文や目的に、前の版・共有していない分析との関係を書かない（同 11）
- 実名を載せるかは規約と共有先で決める（同 12）
- 書いたら依頼者に見せ、合意を取ってから notebook に入る。分析中に設計と変わったら、設計 md を先に直す

## Step 3: 見せて直す

- 材料を読んだら、聞き返す前に計画 md のたたきを一通り書く。目的・優先度・期限は「仮置き」と明記する
- 規約に従って保存し、検査を通す。ユーザーには、目的・現状把握の範囲・仮説の見出しを短く示し、全文は読んでもらう（表が多く、要約では粒度が伝わらない）
- 指摘を受けたら、直す前の版を `git add` でステージしてから直す。直した後に `git diff <ファイル>` でレビューの前後の差分を見せ、合意を得たらもう一度 `git add` してコミットする（`analysis-principles.md` の 2）。直す前の版を上書きしてしまったら、会話に残っている前の版を書き戻してステージし、直した版を戻す
- 指摘は、その文書を直すだけで終わらせない。ほかの分析でも同じ指摘を受けそうなものは、抽象化して `references/analysis-principles.md` に足す（同じ考え方があれば例を足す）。どの回にも当てはまる作り方の方針は、設計 md・レポートでなく skill に入れる
- 指摘を受けたら、型を勝手に変えずに直す。型を変える案があれば並べて選んでもらう
- 未合意の目的・優先度・期限を、決まったこととして書かない

## Step 4: analysis-notebook に渡す

計画の行が、そのまま `analysis-notebook` の問いになる。

| 計画の段 | notebook の分け方 | notebook の問いと回答 |
|---|---|---|
| 現状把握 | 指標のまとまりごとに 1 本（例：業績、人員） | 問い：「指標 X の現状（ばらつき・推移・欠け・他の指標との関係）はどうか」。回答は事実の記述と、仮説検証に渡す気づき。YES／NO は付けない |
| 仮説検証 | 目的ごとに 1 本 | 問い：計画の仮説。判断基準は検証方法から決め、回答は analysis-notebook の回答の型（YES／NO／部分的／まだ言えない） |

- 指標の定義を決める作業は、現状把握の notebook の最初の章にする（既存のスコアの値との突き合わせを含む）
- notebook の結果を受けて、計画 md の優先度・仮説・取りに行くデータを更新する（更新のモード）

## 書き方

- 計画 md は依頼者に見せる前提で書く。規約やグローバルの書き方原則があれば従う
- 表は列で比べる必然があるもの（指標の一覧、仮説の表）に使う。読み方の補足は表の下に箇条書きで置く
- 1 つのセルは 1〜2 行。長くなる注意は表の下の補足へ
- 同じ指標・仮説を複数の場所で名乗らない（現状把握は指標ごと、仮説は目的ごとに 1 回）
