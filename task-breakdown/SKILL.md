# task-breakdown — 規約駆動のタスク整理スキル

タスクの背景・やること・完了条件を、担当者が自分で考えて固められるように支える壁打ち相手。成果物は対象リポジトリの規約が定めるタスクファイル（例: `tasks/yyyymmdd_<slug>.md`）で、Issue の本文に収まらない要件・仕様の置き場。起票は行わない（起票は `task-issue` skill）。

## 絶対ルール（丸投げ自動化しない）

- **未合意の内容を勝手に確定しない。** やること・完了条件の文章を、確認なしに書き上げない。合意できた欄は記入・清書してよい。
- 根拠を添えた提案は出してかまわない（「この完了条件だと検証できないので、〜を確認できた時点、にしてはどうか」）。採否は担当者が決める。
- 議事録・Issue・会話に無い担当・期限・事実を作らない。分からないことは「未確定事項」に番号付きの質問で残す。
- 生データ・個人情報・認証情報・実数値を書かない。
- **Issue・Project 側は読むだけ。** 本文・コメント・担当・期限・親子・close を書き換えない。GitHub 側で手で直した内容が正本で、このスキルが直すのはタスクファイルと台帳の「詳細」列だけ。

## Step 0: 規約ディスカバリ（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指す運用ガイド（例: `docs/guide/project-ops-guide.md`）を Read し、次を組み立てる。規約に明示があればそれに従い、無ければ probe、それでも不明なら聞く。

| 項目 | 取得元 |
|---|---|
| タスクファイルの置き場と命名 | 規約（例: `tasks/yyyymmdd_<slug>.md`。日付は作成日、Issue 番号はファイル名に使わない）。無ければ `tasks/`・`docs/tasks/` を probe |
| タスクファイルの型 | 規約の節構成と frontmatter。無ければ本スキルの既定（Step 3） |
| タスク台帳 | 規約に台帳（例: `tasks/index.md`）があれば、同じテーマの行の ID・出典・状態を読む。保存時に「詳細」列へリンクする |
| タスクのツール | wiki「進行」表の「タスクのツール」行（GitHub Issue ならリポジトリ名を `gh` の `--repo` に使う） |
| 直近の議事録 | 議事録置き場で会議日が最新の 1 本（ネクストアクション表と、そのテーマの議事内容） |
| プロジェクトの「いま」 | `docs/wiki/index.md` の進行表等（やることの粒度・担当・期限の前提） |
| git 運用 | 規約が定めていればブランチを用意し、保存後にコミット案を出す |

既存のタスクファイルを一覧し、同じテーマのファイルがあれば新規に作らず更新として進める（更新箇所を差分で示す）。

## Step 1: 入口を判定する

| 入口 | 何を読むか |
|---|---|
| **Issue 番号**（例: `#10`） | `gh issue view <番号> --repo <org>/<repo> --json title,body,state,assignees,url,comments` と、Sub-issue があればその一覧（`gh api graphql` で `repository.issue(number:).subIssues(first:50) { nodes { number title state } }`）。gh が無ければ本文とコメントを貼ってもらう。frontmatter `issue:` がこの Issue の URL と一致するファイルがあれば Step 1-1 へ |
| **議事録の行**（ファイル名と行番号） | その行と、同じテーマの「議事内容」の小見出し |
| **自由記述** | 会話の内容。目的が読み取れなければ最初の 1 問で聞く |

### 1-1. 更新モード（`issue:` が一致するファイルがあるとき）

Issue 側（本文・コメント・Sub-issue）とファイルの食い違いを、壁打ちの前に表で出す。Issue 側は読むだけで書き換えない。

| 項目 | ファイル | Issue 側 |
|---|---|---|
| やること 3 | 定義の原本で対象範囲を確認する | コメント（9/15）で「範囲は固定、定義だけ確認する」に変更 |
| 完了条件 | wiki の前提に対象範囲が入っている | 本文に無い |
| 子タスク | （#15）（#16） | Sub-issue に #27「除外条件の見直し」が追加 |
| 担当 | PM | assignee が変更 |

- 項目ごとに「ファイル側を直すか、そのままにするか」を聞く。Issue 側の内容をファイルに写すときも、書かれていることだけを写し、要約で意味を変えない。
- 承認後にファイルを更新する（新規作成しない。frontmatter の `date` は変えない）。Sub-issue が増えていれば「やること」に項目を足し、末尾に `（#n）` を付ける。
- 食い違いが無ければ「Issue とファイルは一致しています」と伝えて Step 2 へ。
- 最後の案内（Step 4）に「変更点は Issue #n にコメントで一言（PR の URL）残してください」を足す。

## Step 2: 壁打ちで固める（一問ずつ）

次の欄を、順に 1 問ずつ聞いて固める。既に分かっている欄は確認だけにし、飛ばしてよいものは飛ばす。

| 欄 | 聞くこと・整える基準 |
|---|---|
| 目的 | このタスクが終わると何ができるようになるか（作り手の作業でなく、得られる状態で書く） |
| 背景 | 今なぜ必要か。何ができていなくて、何が妨げられているか |
| やること | 番号付きの箇条書き。1 項目は 1 人が数日で終えられる単位（子タスクになる）。順序に依存があれば番号順に並べる |
| 完了条件 | 検証できる行動で書く（「〜が動く」でなく「〜を実行して〜が出る」）。やることの各項目に対応させる |
| 判断の観点 | 進めながら決めることがあれば、何を見て判断するか |
| 制約・分かっていること | 技術・権限・期限の制約、調べて分かっている事実 |
| 未確定事項 | 埋まらなかった欄を番号付きの質問にする（誰に聞けば決まるかも添える） |

- 詰まったときは切り口を示す（「最小で動く状態は何か」「誰が使って何が変わるか」「やらないことは何か」）。
- やることが 6 項目を超えるときは、親を分けるか提案する。

## Step 3: 保存する（承認後）

内容が固まったら、ファイルの全文を見せて承認を取り、規約の置き場・命名で保存する（日付は今日。既存ファイルの更新なら日付は変えない）。frontmatter は規約のスキーマに従う。規約に型が無いときの既定:

```markdown
---
type: task
title: <日本語タイトル>
date: "YYYY-MM-DD"
status: active
issue: <入口が Issue ならその URL。無ければ空のまま（task-issue skill が埋める）>
related: []
---

# <日本語タイトル>

## 目的

## 背景

## やること

1. <項目>
2. <項目>

## 完了条件

- <やること 1 に対応>

## 判断の観点

## 制約・分かっていること

## 未確定事項

1. <質問>（誰に聞けば決まるか）
```

節に書くことが無ければ、その節は省く。

台帳がある repo では、保存後に台帳の該当行の「詳細」列にこのファイルへの相対リンクを足す。行が無ければ進行中節に 1 行足す（ID は入口が Issue なら `#n`、それ以外は `yyyymmdd-#`。出典は入口が議事録の行ならその行、自由記述なら `壁打ち yyyy-mm-dd`。状態は Issue があれば `登録済み`、無ければ `未登録`）。

## Step 4: 子タスク案を並べ、task-issue へ渡す

「やること」の各項目を子タスク案として、タイトル・担当案・期限案の表で示す。担当・期限は会話で出たものだけを書き、無ければ「未定」。

最後に「起票は `task-issue` skill で行います。このファイルを渡してください」と案内して終わる。更新モードで既存ファイルを直したときは、代わりに「変更点は Issue #n にコメントで一言（PR の URL）残してください。新しく増えた項目があれば `task-issue` skill で子 Issue にできます」と案内する。**このスキルでは Issue を作らず、Issue 側も書き換えない。**

規約に git 運用があれば、保存したファイルと台帳の更新を 1 コミットにする案を示す（メッセージ案を提示して確認後に commit）。
