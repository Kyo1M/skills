# understand — 資料を理解し、説明できるようにする

完成した資料・分析（レポート／設計書／notebook／PDF）を、**ユーザー自身が理解し、相手に説明できる状態**まで対話で導く。grill-me（ユーザーに問い詰める）の逆で、エージェントが教え、**teach-back（ユーザーが自分の言葉で説明し返す）**で理解の定着を確かめる。最後に説明台本・用語と数式・想定問答を explainer として残す。

このスキルは内容を新しく作るものではない。**既にある資料の内容に忠実に**、それをユーザーの頭に入れることが目的。原文に無いことを足さない。

共有前の理解の確認としても使う。規約に共有前の確認の決まりがあれば、それとして使う。teach-back で説明できない記述は、共有する成果物から外す（カットを優先する）判断材料にする。

## 使い方

```
/understand [資料・notebook のパス]
```

パスの指定が無ければ、直近に作成・言及した資料を候補として AskUserQuestion で確かめる。

## Step 0: 規約を読む

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイドを読み、次を決める。

| 項目 | 既定（規約に無いとき） |
|---|---|
| explainer の置き場・名前 | `docs/explainers/YYYYMMDD_<元の名前>_explainer.md`（無ければ作る） |
| frontmatter・検査のコマンド | 無し。規約に必須の項目・lint があれば従う |
| git の運用 | 規約に従う。無ければコミットしない |
| notebook の形式と出力の読み方 | marimo（出力は `__marimo__/session/`）。`analysis-notebook` の形式の references に従う |
| 個人の行・自由記述の原文 | explainer に出さない。分類・集計に言い換える |
| 共有前の確認の決まり | 無し（勧めるだけ） |

## 入力の扱い

- 同じ内容が複数の形式であれば、md を優先して読む（数式・構造が崩れていない）
- **PDF**: `pdftotext <pdf> -` でテキストにして読む。数式は記号が崩れるので、元の md があれば併読する
- **notebook**: 編集対象のファイル（marimo の `.py`、変換型ならスクリプト）を読む。出力は形式の置き場から読む（marimo なら `analysis-notebook/scripts/read_session.py`）。`.ipynb` は直接編集しない
- 読み込んだら、まず内部で**構造マップ**を作る: 章立て／各章の主張／数式／図／章の間の依存関係
- 構造マップは原文に忠実に作る。原文に根拠の無い補完を混ぜない（補うときは「これは原文に無い補足」と明示する）

## 理解のサイクル（固定）

### フェーズ 0: 把握と目的の設定

- 資料を読み、構造マップを作る
- AskUserQuestion で確かめる:
  - **誰に説明するか**（クライアント／共同研究者／自分用／一般）
  - **持ち時間**（30 秒／数分／じっくり）
  - **どこが分かりづらいか**（数式／全体像／なぜこの手法か／用語／特に無し）
- 答えで、解説の深さ・順序・力点を決める

### フェーズ 1: 全体像（トップダウン）

- 「この資料は何を・なぜ・どう示したか」を平易な 1 段落で示す
- 章の役割と依存の地図を短く示す（どの章がどの章の前提か）
- 「ここまでで引っかかる点は？」と確かめてから次へ進む

### フェーズ 2: セクションごとの対話

- 中心のセクション（特に数式・中心的な主張）を、毎回この順で説明する:
  1. **直感**: 一言で言うと何か（記号でなく言葉で）
  2. **数式**: 式を示し、各記号が何かを対応づける（数式が無ければ、指標の計算の仕方）
  3. **なぜ妥当か**: その式・手法が適切な理由
  4. **よくある誤解**: 誤読しやすい点、「意味すること／意味しないこと」
- **1 セクションごとに区切り、ユーザーの質問を受けてから次へ進む**。一度に詰め込まない
- 数式には必ず「一言で言うと」を添える

### フェーズ 3: teach-back（理解の確認）

セクションごと、または一区切りごとに行う。**質問と想定回答を必ず組で示す**（時間を優先する既定の運用）。

1. **質問**: 「今の内容を、説明する相手に話すつもりで、自分の言葉で説明してみてください」。観点は 1 つに絞る（理解度チェックリストから 1 項目）
2. **想定回答**: その質問の模範の答えを、**原文に忠実に**簡潔に示す。引用ブロックや「想定回答」の見出しで区切る。「まず自分で一言 → 想定回答と照合」でも「想定回答を読んで納得」でもよい、と一言添える

- 想定回答は原文の主張に厳密に基づく。原文に無い内容は「これは原文に無い補足」と明示し、「部分的」を YES に丸めない。憶測で模範の答えを作らない
- ユーザーが自分の言葉で説明したら、原文に照らして**正確さ・抜け・誤り**を具体的に指摘する。**質問・指摘は一度に 1 つ**。できるまで繰り返す
- 想定回答を同時に出すと、答えを隠して考えるより定着は弱まる。時間が取れる論点では「先に自分で答える → 後で想定回答」を促してもよい

### フェーズ 4: explainer を作る

- 説明台本・用語と数式・想定問答（FAQ）を作り、Step 0 の置き場に保存する
- 対話で固まった理解・言い回しを反映する（ユーザーが詰まったところは FAQ を厚くする）
- explainer は notebook の外なので、個人の行・自由記述の原文・人数の少ない区分の値を入れない（Step 0 の規約）

### フェーズ 5: 仕上げの確認

- 最後にもう一度 teach-back:「全体を 30 秒で／数分で説明してみてください」。ここでも想定回答（説明台本の要点）を組で示す
- 言えれば完了。まだ曖昧な点は explainer の「残課題」に書く

## 理解度チェックリスト（teach-back の観点）

- [ ] 主張（結論）を一言で言えるか
- [ ] 各数式・指標の意味を言葉で言えるか
- [ ] なぜその手法が妥当かを言えるか
- [ ] 限界・前提を言えるか
- [ ] 想定される反論・よくある誤解に答えられるか
- [ ] 数値の「意味すること／意味しないこと」を区別できるか

## explainer の構成

```markdown
# <元の資料の名前> 説明用 explainer（YYYY-MM-DD）

## 0. 元の資料
- パス、説明する相手、持ち時間

## 1. 説明台本
- 30 秒版／数分版など、相手・持ち時間別に「この順でこう言えば伝わる」箇条書き

## 2. 用語・数式
- 中心の用語・数式を「一言で言うと」の水準で。記号 → 言葉の対応

## 3. 想定問答（FAQ）
- 相手から来そうな質問と模範の答え（対話で詰まった点を厚く）

## 4. 残課題
- まだ曖昧な点、原文で決まっていない点
```

規約に frontmatter の決まりがあれば先頭に付ける。docx や Google Docs で配るときは `docx-export` を案内する（このスキルの責務の外）。

## ガード

- **原文に忠実に**。原文に根拠の無い内容を足さない。曖昧な箇所は「原文では未確定／未言及」と明示する
- teach-back の添削は原文の主張に照らして行う。エージェントの憶測を正解にしない
- 誤解しやすい指標・数値は「意味すること／意味しないこと」を必ず区別する（`analysis-notebook` のガードと同じ）
- 断定を避けるべきところで断定しない。確度の低い説明には「確度: 中／低」と添える
- 一度に多くを詰め込まない。1 セクション・1 問ずつ進める

## 関連

- `grill-me`: 対話の作法（1 問ずつ）
- `analysis-notebook`: 回答検証チェックリスト、notebook の出力の読み方
- `docx-export`: explainer やレポートを docx にする（Google Docs へは手でアップロード）
