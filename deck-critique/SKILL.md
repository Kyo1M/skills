# Deck Critique — 資料の批評・推敲

構成 md や完成 HTML スライドを、**作成した文脈から離れた別の目で検査する**スキル。作った本人(同じ会話)のセルフチェックは自分の判断を追認しがちなので、批評だけを独立の工程として行う。

## 実行方法

- **メイン会話で資料を作った直後なら、Claude のサブエージェントと Codex で並行に批評する**。Agent ツールで批評用のサブエージェントと `codex:codex-rescue`(批評だけを依頼し、修正させない)を同時に起動し、両方に同じ材料を渡す: 本スキルのパス(`~/Developer/Skills/deck-critique/SKILL.md`)、資料ファイル、元素材、会話で決めたことの一覧(下の「入力」)。作成時の経緯・判断理由は渡さない(作った側の判断を追認させないため)。
- メインは 2 つの結果を突き合わせ、指摘を資料と照らして確かめてから 1 つの指摘リストにまとめる。両方が挙げた指摘を優先し、各指摘にどちらから出たかを添える。批評は仕上げに 1 回だけ行う。
- サブエージェントや Codex が使えない環境、またはユーザーから直接レビューを頼まれて作成の会話が無いときは、そのまま本スキルの検査手順を実行する(それでも工程を分ける価値はある)。

## 入力

1. **資料本体**(必須): 構成 md または HTML スライド
2. **元素材**(あれば必ず渡す): ユーザーのアイデアメモ、議事録、決定事項、deck-outline のメモインベントリ(M1…)と、レビュー返答で示したトレーサビリティ。渡されれば脱落突合(検査 4)を行う
3. **会話で決めたことの一覧**(メイン会話から起動するとき): 依頼者と合意した方針・見送ったこと・依頼者の指示で残したもの。決定済みの点は指摘しない(合意と書き方原則が矛盾して見えるときだけ、その旨を 1 行で添える)
4. **読者と場**(任意): 誰向けか、どの会議で使うか。不明なら資料から推定し、推定であることを明示する

## 検査項目(この順で)

### 1. ストーリーの一貫性

- 資料の「狙い」を**本文から逆算で 1 文抽出**する(作成者の意図ではなく、書かれたものから読み取れる主張)。抽出できなければそれ自体が最重要の指摘。
- 各ページの主張が狙いにぶら下がっているかを 1 枚ずつ確認する。ぶら下がらないページ、唐突な対比軸、前のページと接続しない飛躍を指摘する。
- 背景→課題→解決→具体の因果が一本で通っているか。全体も章の中も抽象 → 具体の順に進み、後ろのページの概念に頼るページが先に来ていないか(原則 62)。
- 目的と主要な用語の言い方が全ページで 1 つに揃っているか。語が依頼者のメモ・発言の語になっているか(原則 63)
- 相談が主題の定例で、主題に効かないページ(活動一覧・推進側の実装計画やガントの独立ページ・条件表や考察を並べた検証報告)が残っていないか(原則 61)

### 2. 日本語の自然さ

`deck-outline/references/writing-principles.md` の原則(特に 7)に照らして全ページを検査する:

- タイトル: 体言止めか。動詞締め・比喩ジャーゴン(「背骨」等)・抽象的な体言化(「〜という到達点」)がないか
- リード文(トップメッセージ): 短文の連打になっていないか。結論＋判断理由・結果を 1〜3 行で言っているか(結論 1 文に切り詰めて省略が過ぎていないか、ボディの縮約になっていないか)。改まった語(「本日」等)か
- ボディ: 体言(単語)の羅列がないか。「だから」の多段連鎖がないか。**「太字キーワード ── 説明」の 1 行圧縮・`──`(長いダッシュ)の多用がないか**(タイトルの副題・kicker・箇条書き見出し・ガントのトラック名も)。箇条書きは 1 項目 1〜2 行の短文＋子の箇条書きになっているか
- 全体: 読者の語彙か(専門語・カタカナ抽象語の混入)。声に出して読んで、実際に打ち合わせで人が言う言い回しか
- タイトルが対象を名指す短い名詞句か(「A から B まで」の範囲表現・「広がり」のような抽象語になっていないか)。製品名が正式名で統一されているか(「Copilot」単独 → 「GitHub Copilot」)
- 段階に合った断定度か(たたき・検証中のものを「〜する仕組みです」と言い切っていないか)。仕組みのページのリード文が「作ったもの＋何がどう良くなる見込みか」で締まっているか。工程の各ステップに主体(ヒト／AI)があるか
- レビュー反映が「誰の何の指摘をどう直したか」の表になっていないか(1 文で足りる)。リード文に個人名付きの指摘が無いか。報告ページが前回定例からの変化点を先に書いているか
- 何の、が付かない「標準」「初期値」「準備」「整備」のような語が、見出し・マイルストン名・表の項目名に残っていないか(原則 68)
- 課題・効果の一覧の箇条書きが長くないか。状態を短い 1 文で書き、内訳・原因・例を補足へ移しているか。判断に要る帰結はリード文か本文に残っているか(原則 69・27)
- 項目名・見出し・リード文が経緯(「前回扱えなかった」「積み残し」)で付いていないか(原則 70)

### 3. 議論のしやすさ

- 【議論】ページは 1 ページ 1 決定か。方針(たたき)をボディで示し、聞きたいことをリード文の末尾に改行して 1〜2 文で添えているか(独立の問い欄を置いていないか)
- 方針のたたきに、その場で妥当性を判断できるだけの具体があるか(抽象ラベルへの圧縮が起きていないか)
- 選択肢 A/B/C の並列比較を無許可で持ち込んでいないか(既定は方針の直接提示)
- 「まとめ」ページがあるか。振り返りと持ち帰りが 1 枚に畳まれているか
- 素材に対して内容の過不足・事実の誤り(素材との食い違い・数の不整合・製品の仕様の誤り)がないか(分量・時間枠では判断しない)
- 定例資料で、表紙と振り返りの間に「本日ご相談したいこと」(共有すること／ご相談したいことの箇条書き 1 枚)があるか。議論そのものをアジェンダのページで済ませていないか(議論はテーマのページで、聞くだけのことはまとめの「お伺いしたいこと」へ)。アジェンダの各項目が名詞句で、理由や範囲の説明が足されていないか(deck-outline 原則 67)。依頼者のメモの型(洗い出し等)を作成者が別の型に置き換えていないか
- 今後の分析・次の打ち手・改善案のように案を並べたページで、作り手の考える優先度が見えるか(高い順に上から・太字か優先度の列・リード文で何を優先したいか)。同じ重さの行が多く並んでいないか(deck-outline 原則 79)
- 「p8」「p6〜p8」のようなページ参照が、アジェンダ・目次・章扉・本文・表・まとめのどこかに残っていないか(流用元の指定・TODO 節・フッターの自動番号は除く)。別のページを指す題が実際のページの題と合っているか(手直しでページを足し引きした後に必ず見直す。原則 41・77・80)
- 「ご相談させてください」が議論のページだけにあるか。報告のページに付いていないか、「会話させてください」が残っていないか(原則 12)
- 振り返りの前回の確認事項が「〜とのご意見」でなく「〜を置く」の形の箇条書きか。相談中のものを決まったように書いていないか(原則 36・53)。表のセル・箇条書きで「〜し、〜おき、〜にして」と要素をつないだ 1 文が無いか(原則 7①)
- マイルストンに「M1a」のような記号のラベルが無いか(中身の名前か通し番号か)、マイルストンの表と週次WBSが別ページで重なっていないか(原則 72・78)。検討中の対象の件数を「対象2案件」のように固定していないか(原則 53)。表紙の副題がテーマ単位の短い名詞句か(原則 56)
- 相手に提出する報告資料で、補足・注が結果の読み違いを防ぐものだけになっているか(期間の定義・選び方・統計の数値が残っていないか。原則 15)。リード文に「ご相談させてください」が残っていないか、まとめに合意前の時期・担当が無いか(原則 80)
- 報告資料で、表紙 → エグゼクティブサマリー → 目次の順になっているか。要約のページ名が「エグゼクティブサマリー」か、相談事項だけのページを立てていないか、目次の章名が章扉と同じ語か(deck-outline 原則 80)
- 「〜は次回相談する」の先送りが、今回出せる案の代わりになっていないか。決める予定の無い頻度・件数の先送りを書いていないか(原則 71)
- 導入時期が合意前のマイルストンに案件名が入っていないか。達成したい状態と時期の目安で書かれているか(原則 72)。依頼者がゴールと目的を分けて使うとき、その階層に合っているか(原則 56)

### 4. 脱落の突合(元素材があれば)

- 元素材の項目を番号付きで列挙し、各項目が資料のどのページに反映されたかを突合する
- 反映が見つからない項目を「脱落候補」として列挙する(意図的な省略かの判断は作成者・依頼者に委ねる)
- 元素材の具体(数値・チェック項目・固有名詞)が抽象ラベルに縮んでいる箇所を指摘する
- 構成 md → HTML の場合は、構成 md の各スライド・各ボディ項目が HTML に残っているかを 1 対 1 で突合する(「読みやすさのため」の間引きは脱落候補として列挙する)

### 5. 完結性・その他

- 資料単体で理解できるか(前版差分・社内文脈への暗黙依存がないか)
- TBD・プレースホルダ・空欄の残存
- (報告ページ)実績を文字だけで語っていないか。作ったもの・動いたものの実物(スクショ・出力ファイル・PR 一覧・リポジトリの画面)が 1〜2 枚置かれ、本文がその読み方と結果に絞られているか。実物を画面共有任せにしていないか(pptx に残らない)。画像生成の挿絵で実物の代わりにしていないか(deck-outline 原則 39)
- 読み手に自明なこと(相手が知っている人の肩書き・所属・チーム人数、相手自身からの依頼の経緯、他ページにある日付の再掲)で余白を埋めていないか(原則 40)
- 事実の誤り・数値の不整合(裏取りできるものは自分で確認する)
- (完成 HTML の場合)`data-speaker-notes`(発表者ノート)が残っていないか。内情(守りの理屈・社内事情)がデッキに残っていないか(pptx をクライアントに渡す前提)
- (構成 md の場合)前版差分の節・🆕/✏️/♻️ の区分バッジ・トレーサビリティ表・設計判断の経緯が残っていないか(残す節は「伝えたいこと＋ページの流れ」「全体像テーブル」「実文言」「口頭で補足すること」「TODO」「確認したいこと」)。枠組みそのものに関わる問いが補足に埋もれず「確認したいこと」の先頭にあるか。md の外で増えたページが md に戻っているか、または「以後は pptx が正本」と書かれているか(原則 63)。流用ページが空ページ＋流用元だけになっているか。更新待ちの箇所が「（TODO: …）」で書かれているか。リード文の継続行を空白で字下げしていないか(複数行は子の箇条書きで。原則 66)。表の図版指示に左端の番号か大項目の列があるか(原則 64)

### 6. ビジュアル(完成 HTML の場合)

`html-slide-deck/references/design-system.md` §4〜§5 に照らす:

- スライド右上に役割バッジ(報告／確認／議論／参考／再掲／導入／振り返り／まとめ等)や「画面共有」バッジが残っていないか(役割は構成 md の設計用で表示しない。deck-outline 原則 42)
- 表の一番左の列に番号か大項目があり、同じ大項目が続く行がセル結合されているか(原則 64)
- 表・本文・リード文に 1〜2 文字だけが次の行に落ちる行や、語の途中での折り返しが無いか。リード文・本文・表のセルの行頭に空白が無いか(原則 65・66。pptx でも同じ点検をする)
- アイコンの置き場所が見出し帯カードの見出し(と章扉の章名)に限られているか。箇条書きの各行・工程ノード・表の行や行グループ名・表紙の流れ・目次・文中・タイトル横に付いていないか
- アイコンは既定 0 個か。構成 md に指示がある枚だけ、見出し帯カードの見出しに 1 枚 0〜4 個で置いているか(5 個以上は多すぎる)。同じ概念に別のアイコンを使っていないか(`icons.md` の対応表と照合)
- 文字だけの枚が続き、構造(表・進行表・ステップ・カード列)で受け止められるのに受け止めていない箇所がないか。逆に 1 枚 1 テーマを割ってまで分割していないか
- 塗りボックスが 1 枚に 4 個以上並んでいないか。Klein Blue が要所(推奨・本命・キー数値・現在地・強調語句)以外に広がっていないか
- 機械チェック(`html-slide-deck/assets/check-slides.mjs`)の FAIL が残っていないか(結果が添えられていなければ自分で回す)

## 出力フォーマット

**勝手に修正しない。** 以下の形式で指摘リストを返し、修正の取捨選択は依頼者に委ねる:

```
## 総評(2〜3 文: 狙いの逆算結果と、最も効く改善 1 点)

## 指摘(重要度順)
1. [重大|中|軽微] <ページ#> <指摘の一文>
   - なぜ問題か: ...
   - 修正案: <実文言のたたき>

## 脱落候補(元素材があれば)
- <素材項目> → 反映先が見つからない(意図的なら OK)

## 良い点(2〜3 点、維持すべき判断)
```

指摘には必ず**実文言の修正案**を添える(「自然にする」のような抽象指示で終えない)。重大 = ストーリーが壊れている・議論が空転する / 中 = 読者が引っかかる / 軽微 = 磨き。

## 他スキルとの関係

- `deck-outline`(構成設計)→ `html-slide-deck` / Claude Design(実装)→ **本スキル(批評)** の順で使うのが基本線。構成段階(md)と実装後(HTML)のどちらにもかけられる。
- 批評の観点の正本は `deck-outline/references/writing-principles.md`。原則が更新されたら本スキルの検査は自動的にそれに従う(原則をコピーせず参照する)。
