# table-definition — 規約駆動のテーブル定義整理スキル

分析で使うテーブルの **構造**（何のテーブルで、1 行が何を表すか、主なキーは何か、どんな列があり、他のテーブルとどうつながり、使うときに何に気をつけるか）を、担当者と一緒に整理してリポジトリに残す。値の中身や ID そのものは扱わない。

出力は二層。詳細は 1 論理テーブル 1 YAML、一覧は wiki の「データ」表（データ・粒度・主なキー・注意点）。型の既定は `references/table-schema.md`。

## 絶対ルール

- **値の中身・具体の ID・実数値を書かない。** 件数・欠損率・最小・最大などの数値プロファイルや値のサンプルは、定義書に載っていても YAML に写さない（注意点に「年齢列はほぼ欠損」のように定性で書く）。会話の中でも読み上げない。
- 分からない項目は「要確認」と書き、推測で埋めない。
- YAML の保存と wiki の反映は担当者の承認を得てから行う。承認前に書き換えない。
- 定義書の原本と生変換した Markdown はコミットしない。

## Step 0: 規約ディスカバリ（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指す運用ガイドを Read し、次を組み立てる。規約に明示があればそれに従い、無ければ probe、それでも無ければ既定を提案して承認を取る。

| 項目 | 取得元 / 既定 |
|---|---|
| YAML の置き場と命名 | 規約。無ければ `docs/tables/` を probe。無ければ既定 `docs/tables/<slug>.yaml`（`slug` は論理テーブル名の英語 kebab-case。`name` と同じ） |
| YAML の型 | 規約の型。無ければ `references/table-schema.md` の既定 |
| 一覧の置き場 | 規約の wiki「データ」表。無ければ `docs/wiki/index.md` に「データ」節（データ・粒度・主なキー・注意点。「用語」の次）を新設する案を出す |
| 索引 | `llms.txt` に「Data」節があれば追記対象。無ければ新設案に「Data」節の追加を含める |
| 使うエンジン | 規約か wiki に書かれていればそれ。無ければ Step 1 で 1 回聞く（`columns[].type` の物理型の表記に使う） |
| 原本の置き場 | 規約にコミットしない置き場（例: `docs/references/`、`.gitignore` 済み）があればそこ。無ければリポジトリ外に置いてもらう |
| 分析設計書・レビュー観点 | 規約にあれば、Step 5 で「想定する集計がこの粒度・キーでできるか」を照らす材料にする。無ければ Step 5 は省く |
| git 運用 | 規約が定めていればブランチを用意し、保存後にコミット案を出す |

規約に置き場が無い repo では、初回に次をまとめて 1 回で承認を取り、承認後に足す（規約に「正本と転写先の同期ルール」があれば、その転写先にも同じ行を写す）。

- `docs/tables/` を新設する
- `AGENTS.md`: ディレクトリ構造のツリーと「ディレクトリの選び方」表に 1 行、命名規約の例外（`docs/tables/<slug>.yaml` は日付プレフィックス無し）に 1 行、frontmatter の種別に `table`（YAML。lint の対象外）を 1 行
- `docs/wiki/index.md`: 「データ」節の新設と、「歩き方」表への 1 行
- `llms.txt`: 「Data」節の新設
- `README.md` の早見表にディレクトリ行があれば 1 行

## Step 1: 入力を確認する

最初に「テーブル定義書はありますか（Excel・DDL・CSV のヘッダ・画面のコピーなど）」と聞く。

- **Excel**: 原本はコミットしない置き場に置いてもらい、Markdown に生変換してから読む（例: `markitdown "<定義書>.xlsx" -o <置き場>/<名前>-raw.md`。変換ツールが無ければ、必要なシートを CSV に書き出すか列名の一覧を貼ってもらう）。生変換の読み方は `references/table-schema.md` 末尾。
- **DDL・CSV のヘッダ・口頭説明**: そのまま読み取る。定義書が無くても、担当者の説明から同じ型に落とせる。貼り付けられたテキストは `derived_from` に「貼り付けの DDL」などと書き、見比べは貼り付け元と行う。
- 使うエンジン（BigQuery・Snowflake・PostgreSQL など）が規約に無ければ、ここで 1 回聞く。
- 何も無い場合: wiki「データ」表で「要確認」になっている行を出発点にしてよいか確認する。

## Step 2: 対象を絞る

テーブルが多いときは、先に一覧（論理テーブル名・粒度・物理名）を出して、**今回 YAML にするテーブルを担当者と合意**する。分析で使う見込みの無いテーブルまで作らない。

## Step 3: 1 テーブルずつ YAML の案を出す

規約の型（無ければ `references/table-schema.md`）で、1 テーブルずつ案を提示する（一度に全部埋めて渡さない）。分からない項目は「要確認」。

- `columns[].type` は使うエンジンの物理型をそのまま書く。
- 分からない項目の書き方: 文字列の項目（`grain`・`type`・`description`）は「要確認」。配列の項目（`keys.primary` など）は空配列にし、`notes` に「主キーは要確認（store_code・sales_date で一意か）」のように 1 行置く。参照先が分からない `relations` は行を作らず、`notes` に「item_code の参照先（商品マスタ）は未提供」と書く。列の `note` は注意が無ければ空文字でよい。
- テーブル名や NOT NULL 列からの見立て（粒度・主キーの候補）は書いてよいが、「（見立て。要確認）」を付ける。担当者の回答から導いた解釈も、回答そのものと分けて書く。
- 「注意点」は、知らないと後で集計を作り直すことになりやすい情報（欠損が多い、重複しやすい、更新タイミングがずれる、対象外レコードが混ざる、換算方向が未確認、など）。定義書に無くても一言確認する。
- 定義書の中で表記がぶれている箇所（同じ列が別名で出る、テーブル名が入れ替わっている等）は `notes` に「要確認」として残す。
- 同じ構造の物理テーブルが複数ある（国別・年別など）ときは 1 つの論理テーブルにまとめ、`physical_names` に列挙する。

## Step 4: 保存する（承認後）

承認された YAML だけを置き場に `status: draft` で保存する。保存後、「原本と見比べて問題なければ `status: active` に変えてください」と案内する。

## Step 5: 想定する集計ができるか確認する（材料があるときだけ）

分析設計書、または wiki の未解決論点・タスクファイルに書かれた集計の論点と照らして、「このテーブルの粒度・キーで、想定する集計ができそうか」を一言確認する。難しそうなら、その旨を `notes` に残す。材料が無ければ省く。

## Step 6: wiki と索引に反映する

- wiki「データ」表に、1 論理テーブル 1 行で **変更前 → 変更後の差分の形** で提示し、承認されたものだけ反映する。データ列は YAML へのリンク。主キーが未確認なら「要確認（結合: …）」。規約に「直近更新」節があれば、その 1 行も差分に含める。
- `llms.txt` の「Data」節に `- [<title>](./docs/tables/<slug>.yaml): <粒度>` の形で 1 行追記する（機械的な索引更新なので承認を待たなくてよい）。

## Step 7: 完了

1. 規約に lint があれば実行する。
2. 変更したファイルの一覧を示す。
3. 次を案内する: 定義書が更新されたら同じ手順で差分更新する（`date` を更新し、変わった列だけ直す）。集計クエリや分析設計を書くときは該当 YAML を読む。
4. 規約に git 運用があれば、その定めどおりにブランチ（既定 `wiki/<yyyymmdd>-tables-<slug>`）で YAML と wiki・索引の更新を 1 コミットにする案を出す（メッセージ案を提示して確認後に commit。push・PR は規約の定めに従い、提案止まりの規約なら提案だけ）。
