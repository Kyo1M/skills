# metric-definition — 規約駆動の指標の定義整理スキル

分析で使う指標の **計算方法**（何をどう数えるか、分子と分母、対象に含める条件、期間や区分でまとめるときの取り方）を、担当者と一緒に整理してリポジトリに残す。分析の計画・集計のクエリ・レビューが同じ定義を見るようにし、同じ指標を集計ごとに違う取り方で計算するのを防ぐ。指標の値そのものは扱わない。

出力は二層。詳細は 1 指標 1 YAML、一覧は wiki の「用語」表（用語の列から YAML へリンク）。型の既定は `references/metric-schema.md`（正本は project-context-template の `docs/guide/data-definition-guide.md` 3 章。そのガイドを持つリポジトリでは、ガイドを読む）。

## 絶対ルール

- **値・ID・件数を書かない。** 突き合わせの結果も「すべて一致した」「月末の扱いでずれた」のように定性で書く。会話の中でも読み上げない。閾値と区分の切れ目は事業上の決めごととして書いてよい。
- 分からない項目は「要確認」と書き、推測で埋めない。どの取り方を正とするかは担当者が決める。
- YAML の保存と wiki の反映は担当者の承認を得てから行う。承認前に書き換えない。
- 確認クエリは会話の中で示すだけで、実行も保存もしない。実行は担当者が分析環境で行う。
- 定義書の原本と生変換した Markdown はコミットしない。
- 読むファイルを広げない。担当者が指定したファイルと、規約・ガイド・wiki の表・既存の YAML だけを読む。足りない定義は探しに行かず「要確認」として並べ、案を出す前にまとめて 1 回で聞く。

## Step 0: 規約ディスカバリ（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイド（例: `docs/guide/data-definition-guide.md`）を Read し、次を組み立てる。規約に明示があればそれに従い、無ければ probe、それでも無ければ既定を提案して承認を取る。

| 項目 | 取得元 / 既定 |
|---|---|
| YAML の置き場と命名 | 規約。無ければ `docs/metrics/` を probe。無ければ既定 `docs/metrics/<slug>.yaml`（`slug` は指標名の英語 kebab-case。`name` と同じ） |
| YAML の型 | 規約・ガイドの型。無ければ `references/metric-schema.md` の既定。規約の型に既定に無い項目（計算の関数名・別システムとの対応・切り口の定義など）があれば、それも埋める |
| 一覧の置き場 | 規約の wiki「用語」表（呼び名が「用語・指標」などでも同じ表を使い、名前は変えない）。無ければ `docs/wiki/index.md` の「用語」表に行を足す案を出す |
| 索引 | `llms.txt` に「Metrics」節があれば追記対象。無ければ新設案に「Metrics」節（「Data」節の次）の追加を含める |
| テーブル定義 | 規約が指す場所（例: `docs/tables/`）。`tables` 欄に slug を書き、`population` の条件の照合に使う |
| 原本の置き場 | 規約にコミットしない置き場（例: `docs/references/`、`.gitignore` 済み）があればそこ。無ければリポジトリ外に置いてもらう |
| git 運用 | 規約が定めていればブランチを用意し、保存後にコミット案を出す |

規約に置き場が無い repo では、初回に次をまとめて 1 回で承認を取り、承認後に足す。ガイドに「初めて使うときに足すもの」があればそれに従い、無ければ次の既定を使う（規約に「正本と転写先の同期ルール」があれば、その転写先にも同じ行を写す）。

- `docs/metrics/` を新設する（最初の YAML と一緒に作る）
- `AGENTS.md`: ディレクトリ構造のツリーに 1 行。規約に `docs/metrics/` の説明が無ければ「ディレクトリの選び方」表に 1 行、命名規約の例外（日付プレフィックス無し）に 1 行
- `docs/wiki/index.md`: 「歩き方」表への 1 行
- `llms.txt`: 「Metrics」節の新設
- `README.md` の早見表にディレクトリ行があれば 1 行

## Step 1: 何を作るかを伝え、入力を選ぶ

最初に「指標の定義は、式・分子と分母・対象・束ね方を 1 指標 1 ファイルで書いたもので、集計とレビューが同じ定義を見るためのもの」と 2 行で伝え、規約・ガイドに記載例があればその場所を添える。続けて、次のどれから起こすかを聞く（依頼文で入力が分かれば聞かずに進める）。

- **(A) 既存の SQL から起こす**: その指標をよく使う SQL・正だと思う SQL を 2〜3 本指定してもらう。指定が無ければ、指標名（日本語名・列名の候補）で grep して該当行のある SQL の一覧（パスと該当行数）を出し、どれを読むかを 1 回で確かめてから読む。SQL のフォルダを順に開かない。
- **(B) 指標定義書から起こす**: Excel は原本をコミットしない置き場に置いてもらい、Markdown に生変換してから読む（例: `markitdown "<定義書>.xlsx" -o <置き場>/<名前>-raw.md`。変換ツールが無ければ、必要なシートを CSV に書き出すか定義の部分を貼ってもらう）。表題行・`Unnamed`・`NaN` は読み飛ばす。値が並ぶシート（実績表など）は読まない。
- **(C) 分析設計・担当者の説明から起こす**: 分析設計や計画の指標の一覧を読むか、数え方を口頭で聞く。

## Step 2: 対象を絞る

候補の指標を次の表で一覧にし、**今回 YAML にする指標を担当者と合意**する。最初は 2〜3 個を勧める（一度に増やすと、取り方の割れを確かめきれない）。`llms.txt` の「Metrics」節や置き場に同じ指標がすでにあれば、その YAML を読み、新しく作らずに差分更新として扱う。

| 指標名 | 出てくる SQL・資料 | 取り方が割れているか |
|--------|--------------------|----------------------|
| <指標名> | <パスかシート名> | <割れている／揃っている／要確認> |

## Step 3: 1 指標ずつ YAML の案を出す

規約の型（無ければ `references/metric-schema.md`）で、1 指標ずつ案を提示する（一度に全部埋めて渡さない）。分からない項目は「要確認」。

- `definition` には 1 行の式に加えて、期間に入れる日付の列・基準日（いつ時点の値か、起点の日）・通貨・税込か税抜か・返品の扱いのように、取り方で値が変わる決めごとを書く。SQL のコメントにしか無い決めごとも、`definition` か `notes` に移す。
- `basis` は 6 つ（`ratio_of_sums`・`sum`・`recount`・`snapshot`・`weighted_avg`・`simple_avg`）から 1 つ選ぶ。率の指標で月ごとの率を平均していないか、ユニーク数を月の値の足し算で作っていないかを、ここで確かめる。
- `population` の条件が wiki の「用語」表に定義されている（社員アカウントの除外など）なら、その用語を名指しして参照する。
- **(A) で起こすときは、同じ指標の取り方が SQL によって違う箇所**（数え方・除外条件・日付の列・基準日・通貨）を次の形で並べ、どれを正とするかを担当者に聞く。正とした取り方の SQL を `derived_from` の先頭に書き、採らなかった取り方は `notes` に残す。どちらも使うなら別の slug にする（例: `annual-sales-local`・`annual-sales-jpy`）。

  | 違う箇所 | SQL ①（パス） | SQL ②（パス） |
  |----------|---------------|---------------|
  | <数え方など> | <取り方> | <取り方> |

- 区分の切れ目（回数の区分・金額の帯）は、その指標の `bands` に書く。wiki に区分の行があれば、Step 6 でその行をこの YAML へのリンクにする。
- 使うテーブルの定義が置き場に無ければ、先に `table-definition` で整理することを勧める。無いまま進めるなら `tables` に「要確認」と書く。

## Step 4: 突き合わせ先を決める

定義が固まったら、突き合わせ先（クライアントのレポート・定義書の値・既存の SQL の出力）を担当者と決め、そのまま実行できる確認クエリを会話の中で示す（保存はしない）。担当者が分析環境で流した結果を、数値を貼らずに「一致した」「どの期間・区分で、どちら向きにずれた」の形で聞き、`checks` に要点を定性で書く。

- 突き合わせを後に回すときは `checks: []` で保存する。
- 突き合わせ先が無い指標は `against: なし（理由）` と書く。人が定義を確かめたら `active` にしてよいと伝える。
- 突き合わせで合わないときは、理由が分かるまで `status: draft` のままにする。

## Step 5: 保存する（承認後）

承認された YAML だけを置き場に `status: draft` で保存する。保存後、「突き合わせが済んで定義を確かめたら `status: active` に変えてください」と案内する。

## Step 6: wiki と索引に反映する

- wiki「用語」表に、1 指標 1 行で **変更前 → 変更後の差分の形** で提示し、承認されたものだけ反映する。用語の列を YAML へのリンクにし、定義の列には 1 行の式と束ね方だけを書く。区分の行がすでにあれば、定義の列を YAML の `bands` へのリンクに置き換える。規約に「直近更新」節があれば、その 1 行も差分に含める。
- `llms.txt` の「Metrics」節に `- [<title>](./docs/metrics/<slug>.yaml): <1 行の式>` の形で 1 行追記する（機械的な索引更新なので承認を待たなくてよい）。

## Step 7: 完了

1. 規約に lint があれば実行する。
2. 変更したファイルの一覧を示す。
3. 次を案内する: 集計のクエリや分析設計を書くときは該当 YAML を読み、式・母集団・束ね方に沿って書く。定義書や決めごとが変わったら同じ手順で差分更新する（`date` を更新し、変わった項目だけ直す。食い違いは `notes` に書く）。
4. 規約に git 運用があれば、その定めどおりにブランチ（既定 `wiki/<yyyymmdd>-metrics-<slug>`）で YAML と wiki・索引の更新を 1 コミットにする案を出す（メッセージ案を提示して確認後に commit。push・PR は規約の定めに従い、提案止まりの規約なら提案だけ）。
