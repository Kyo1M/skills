# analysis-report — 分析 notebook からレポートを作る

`analysis-notebook` で作った問い駆動の notebook の結果を、Markdown のレポートに組み立て直す。レポートはリポジトリの md を正本にする。共有のために docx にする（Google Docs に上げる）ときは `docx-export` を使う。

レポートは notebook のまとめ表と各問いの回答を一次ソースにする。答えていないことを勝手に補わない。

## 使い方

```
/analysis-report [notebook のパス]
```

## 入力のモード

- **新規作成**: notebook の結論からレポートを組む
- **コメント付きの原稿の改訂**: 依頼者が原稿に書き込んだコメント（本文中の「コメント：」「（→…）」「（…？）」や、行番号つきのコメント一覧）を読み、改訂の前に次の 3 つに仕分けて見せる
  - md で直せる（構成・語・図と本文の食い違い・数値のそろえ方・言い過ぎの結論）
  - notebook でやり直す・足す（新しい図、水準の指標、条件をそろえた比較）
  - 相手に確かめる（データの持ち主・判断する人にしか答えられないこと）
- コメントには 1 件ずつ「同意／一部同意／異論」と理由を返す。言われた通りに直すだけにせず、データや既存の決定と合わない指摘は根拠を添えて返す
- 改訂を始める前に、レビューを受けた版を `git add` でステージする。直した後は `git diff <ファイル>` でレビューの前後の差分を見せる（`analysis-plan/references/analysis-principles.md` の 2）
- 改訂で出た学びのうち、ほかの分析でも効くものは、抽象化して `analysis-plan/references/analysis-principles.md` に足すか、このスキル・`analysis-plan`・`analysis-notebook` のどこか 1 か所に足す

## Step 0: 規約を読む（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイドを読み、次を決める。規約に明示があればそれに従い、無ければ既定を使う。

| 項目 | 既定（規約に無いとき） |
|---|---|
| notebook の形式と出力の読み方 | marimo（出力は `__marimo__/session/`）。`analysis-notebook` の形式の references に従う |
| レポートの読み手の型 | 聞く（クライアント向け → `references/reader-client.md`、研究者向け → `references/reader-researcher.md`）。答えは AGENTS.md に足す案として出す |
| 置き場・名前 | `docs/reports/YYYYMMDD_<name>/YYYYMMDD_<name>.md`、図は同じフォルダの `figs/` |
| frontmatter | 無し。規約に必須の項目・種別の一覧があれば従う |
| 検査のコマンド | 無し。規約に lint などがあれば保存後に通す |
| git の運用 | 規約に従う。無ければコミットしない |
| 個人の行・自由記述の原文 | レポート（本文・表・図）に出さない。分類・集計に言い換える |
| 人数の少ない集計値 | 個人が推測できる少人数の区分（目安 5 人未満）は、載せる前にユーザーに確かめる |
| 外に出してよいかの確認 | レポートと図を保存する前に、載せてよい粒度をユーザーに確かめる。規約に確認の相手（クライアントの担当者など）があれば、その確認を済ませたかを聞く |
| 他の成果物 | 上書きせず、新しい日付のファイルで並べる |
| 共有前の理解の確認 | `understand` を勧める（規約が必須にしていれば必須） |

## Step 1: 一次ソースを読む

先に `analysis-plan/references/analysis-principles.md`（分析の考え方）と、この分析の設計 md（`analysis-plan` の分析設計）を読む。設計 md が無ければ、レポートの目次を決める前に作るよう提案する。

読む順番:

1. notebook のまとめ表
2. 各「問い N への回答」
3. その問いの根拠になっている図表
4. 補助分析や探索の出力

- まとめ表が無いときだけ、各回答から組み立てる。途中の出力や図だけを見て結論を作らない
- 出力は実行した結果から読む。marimo なら、書く前に `analysis-notebook` の手順（`export session --force-overwrite`）で再実行し、`analysis-notebook/scripts/read_session.py` で読む。古い出力のまま書かない
- 数値は実行の結果から引く。notebook の説明文やコードのコメントに残った概数を出典にしない

## Step 2: 構成を決める

構成は設計 md のレポートの目次から始め、notebook の結果に合わせて直す（目次から章を外す・足すときは、設計 md も直す）。章立ては読み手の型の references に従う。どちらの型にも次を入れる。

- **問いごとの結果**: 問い／回答／根拠／限界
- **総合解釈**:
  - 問い同士の関係
  - 何が言えて、何がまだ言えないか
  - 結果が上位の問い（判断・研究の目的）にとって何を意味するか（数値の再掲でなく解釈）
  - その解釈と競合する説明（交絡・データの偏り・手法の仮定）の検討
  - 結果から次に立てる問い
- **次アクション**: notebook が提案した次の確認事項
- **再現情報**（末尾に短く）: notebook のパス、データを確かめた日、図のパス

1 レポートで共有・確認したいことは 1 つに絞る（1 論点主義）。論点が複数あれば分ける。

章には番号を振る（「1. 業績」「1.1 予算達成率の推移」）。読み手がコメントで場所を指せるようにするため。

## 段階に合った結論の強さ

- 現状把握の段のレポートは、冒頭の見出しを「結論」でなく「概要」にする。判断の前提（期間・欠け・何をそろえていないか）は概要の最初に置く
- 検出できない設計で「関係が見えなかった」ことから、分析の焦点の変更や優先度の結論を出さない。例えば、店舗ごとの平均の相関しか見ていないなら、言えるのは「この見方では見えない」まで。焦点の案は「次に確かめること」に置き、どの設計なら見えるかを添える
- 判断する人がすでに持っている見立て（例：人への投資が業績につながる）を、弱い設計の結果で外す書き方をしない。見立てを確かめる設計を次の問いとして出す
- 比率の指標（予算達成率・前年比など）で店舗の差を見たときは、分母が店の水準を割り落としていることを書く。分母の決め方（予算の組み方など）が分からなければ、それを確かめることとして書く

## 記述の決まり

- 回答は `問い / 回答 / 根拠 / 限界` を基本形にする
- 未解決の問いは「未解決」と書く。「部分的」を YES に丸めない
- 補助分析は、確度や解釈にどう寄与するかを 1 文で書く
- **コードの内部の語をそのまま本文に出さない**。変数名・状態名は、何が起きているかを日本語で言い換える。どうしても要るなら初出で定義する
- **内部の資料・作業の名前を本文に出さない**。設計資料の版（「v6」）、PR 番号、データの置き場の名前（「bitemporal」「raw_value」）、関係者のやり取りの名前は書かない。「店舗スコアの元の値」「7 月の分析」のように、読み手が分かる言い方にする
- **分析者の作業語を業務の言葉に直す**。「窓」→「直近 12 か月で数える」、「持ち分」→「総合点の差のうちそのカテゴリで説明できる割合」のように、読み手が普段使う語で書く
- **同じ指標の組には 1 つの計算方法と 1 つの値を使う**。notebook によって相関の方法（順位か値か）や店舗の代表値（平均か中央値か）が違うと、同じ組に 2 つの値が出る。レポートでは 1 つにそろえ、どの方法かを書く
- **具体から集計の順に並べる**。1 つのまとまりの中で、推移と対象ごとの実数（図・表）を先に、代表値・割合への分解・相関を後に置く。全体の図の後に、分け方ごとのサブプロット（月ごと・グループごと）を続ける（`analysis-plan/references/analysis-principles.md` の 8・9）
- **要約の値（中央値など）を採る前に、内訳とばらつきを見せる**。事業部・店舗ごとの内訳を図で出してから、評価にその要約の値を使ってよいかを書く
- **割合だけで比べない**。割合は母数の違う店を同じ重さで並べるので、件数・金額などの水準も添える
- **進行管理の語を本文に書かない**。決定日、会議への言及、「宿題」「積み残し」「前回のご指摘への回答」は作業の層に属する。問われた点は、答えを事実として本文に溶かして書き、「ご質問への回答です」と断らない
- **口語的・比喩的な語を使わない**。中立的な語を選ぶ
- **用語を本文・図の凡例・表のキャプションでそろえる**。図は notebook 側にあるので、本文だけ直して図が古いまま、を起こさない
- **作業の層と共有の層を分ける**。出所・理解度のタグや未消化の点の棚卸しはレポートに出さない。AI が補った導出・主張を確定として書かず、未消化の部分は「要確認」として扱う
- **定型の構造を避ける**。確認したいことは本文に入れてよいが、機械的な見出しや定型の箱にせず、地の文に溶かす。過剰な見出し・全項目同型の表・冗長な前置きを避ける
- **レポートはそれだけで完結させる**。前の版のレポートや、読み手に共有していない分析との関係（「前回のレポートをやり直したもの」「前の分析の素材を使う」）を本文に書かない。依頼者が関係を書くよう指示したときだけ書く
- **分析の標準の用語を使う**。欠損・内訳・分布のような語を、平易にしようとして言い換えない（「欠け」「データの入り方」）。業務に固有の指標（人時売上など）は初出で定義する
- **読み手に渡る文書として書く**。相手を三人称にして「〇〇に渡す」と書かない。相手の見立てと分析者のたたきを書き分ける。既存のロジックへの提言は「改善の余地があれば」の構えで、見えたことと対応の案を組にする（同 10・16・18）
- **深掘りしない論点は最後の節にまとめる**。「残論点・追加分析の候補」に、見ること・使うデータを 1 行ずつ置く（同 17）
- **付録は必須にしない**。作る場合も本文だけで完結させ、「付録に回す」「詳細は付録 B に」で本文の話を中断しない

## 事実の裏取り（本文に書く前に確かめる）

固有名詞・件数・定数は、書く前に一次ソースに当てる。推測で埋めない。

- **外部データは初出で正式名称を書く**。略語を推測で展開しない。元データのファイル名・同じリポジトリの過去のレポート・一次資料と照らしてから書く。調査なら実施回・年・対象まで添える
- **母数・件数は実数で書く**。「約 4,000 件」のように丸めない。数え方が複数ある（全体／除外後／集計に寄与した分）ときは、どれを指すかを明示し、必要なら内訳を並べる
- **結果に効く定数（重み・閾値・正規化など）は、出所と役割を 1 文で書けるまで調べてから本文に出す**。既定値のまま・前の版からの引き継ぎなら、そう書く。書けないものを本文に出さない

## 持ち出しのガード（書く前と保存の前）

レポートは notebook の外なので、Step 0 の規約に従って次を確かめる。

- 個人の行、自由記述の原文、コードに書いてはいけない値（ID・個人を指す値・規約が足す値）が、本文・表・図に入っていないか。入っていれば分類・集計に言い換える
- 人数の少ない区分の集計値が入っていないか。入っていれば、載せてよいかをユーザーに確かめる
- 載せてよい粒度を確かめたか（規約に確認の相手があれば、その確認を済ませたか）

## 図の扱い

- **主張 1 つに図 1 つ**を基本にする。図の無い主張と、主張の無い図の両方を残さない。図の枚数は増えてよい。根拠にならない探索の図は並べない
- 図は主張から選ぶ。「3 月に集中する」なら月ごとの時系列、「店で差がある」なら事業部・店舗の内訳と分布、「構成が偏る」なら 100% の積み上げ棒、「入社月で定着が違う」なら入社月ごとの時系列。手元にある図を流用するときも、その主張が図から直感的に読めるかで選ぶ
- 2 つの分け方（店舗の差と月の動き、など）を 1 つの図に重ねて分かりにくくなるなら、図を分ける
- 図の直前に、その図がどの問いに効くかを書く
- **図の説明を書く前に、書き出した png を開いて見る**。色・凡例・軸・単位が本文の説明（「青の棒は…」）と合っているかを確かめる。notebook で図の色を変えたら本文も直す。行列の図（相関のヒートマップ）は、行と列がそれぞれ何かを書く（結果の側に置いた項目が行に無いと、読み手は抜けたと読む）
- 説明だけで終わっている項目（件数の推移・信号の付き方など）には図を足す
- 図には、可視化の目的・計算の仕方・わかったことを添える。横軸・縦軸が何か、集約の仕方（平均か重み付きか等）を本文かキャプションに書き、その図から何が言えるかを 1〜2 文で書く。図を貼るだけ・キャプションが題名だけ、にしない
- データの確認事項（欠け・ずれ・想定外の値）も、図か、データの入り方が分かる抜粋の表で示す。抜粋は Step 0 の規約に従い、個人の行を出さず、ID はハッシュ・店舗は「店舗 A」のように置き換える
- 参照は `![キャプション](相対パス)` にそろえる（`docx-export` がこの形を読む）
- 図は notebook の中で png に書き出す（書き方は `analysis-notebook` の形式の references）

## Step 3: 保存と仕上げ

保存の前に、読み手の聞き返しを先回りする点検を 1 回通す（`analysis-plan/references/analysis-principles.md` の 15）。概要と各節の主張を一文ずつ読み、次のどれかに答えていない文を直す。

| 聞き返し | 直し方 |
|---|---|
| 「〇〇とは？」（固有の語・社内の語・作業の言い回し） | 初出で定義する。作業の言い回しは 1 つの具体例に置き換える |
| 「内訳は？」（「13 の KPI」「10 分野」「6 店舗」） | 括弧で中身を並べる。名前の付く対象は一覧の表を出す |
| 「いつ？」（「2 回」「年 3 回」「最近」） | 日付・月を書く |
| 「どこのデータ？」 | 出典（システム・取り込み・誰の資料か）を書く |
| 「どの図で分かる？」 | 主張に対応する図表を本文に置くか、付録を指す |
| 「さっきと矛盾しない？」 | 概要の文を本文の図表と照らし、条件をつけた 2 文に分ける |
| 「それは誰の考え？」 | 相手の見立てか、分析者のたたきかを書く |

- 置き場・名前・frontmatter は Step 0 の規約に従う。他の成果物は上書きせず、新しい日付のファイルで並べる
- 規約に検査のコマンドがあれば通す。git の運用も規約に従う
- 共有の前に `understand` で、本文の各主張をユーザーが自分の言葉で説明できるかを確かめるよう勧める。説明できない記述は本文から外す（カットを優先する）。なぜ未解決かを説明できる論点は残してよい
- docx や Google Docs で渡すときは `docx-export` を案内する
