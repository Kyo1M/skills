# analysis-report — 分析 notebook からレポートを作る

`analysis-notebook` で作った問い駆動の notebook の結果を、Markdown のレポートに組み立て直す。レポートはリポジトリの md を正本にする。共有のために docx にする（Google Docs に上げる）ときは `docx-export` を使う。

レポートは notebook のまとめ表と各問いの回答を一次ソースにする。答えていないことを勝手に補わない。

## 使い方

```
/analysis-report [notebook のパス]
```

## Step 0: 規約を読む（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイドを読み、次を決める。規約に明示があればそれに従い、無ければ既定を使う。

| 項目 | 既定（規約に無いとき） |
|---|---|
| notebook の形式と出力の読み方 | marimo（出力は `__marimo__/session/`）。`analysis-notebook` の形式の references に従う |
| レポートの読み手の型 | 聞く（クライアント向け → `references/reader-client.md`、研究者向け → `references/reader-researcher.md`）。答えは AGENTS.md に足す案として出す |
| 置き場・名前 | `docs/reports/YYYYMMDD_<name>/YYYYMMDD_<name>.md`、図は同じフォルダの `figs/` |
| frontmatter | 無し。規約に必須の項目・種別の一覧があれば従う |
| 検査のコマンド | 無し。規約に lint などがあれば保存後に通す |
| git の運用 | 規約に従う。無ければコミットしない |
| 個人の行・自由記述の原文 | レポート（本文・表・図）に出さない。分類・集計に言い換える |
| 人数の少ない集計値 | 個人が推測できる少人数の区分（目安 5 人未満）は、載せる前にユーザーに確かめる |
| 外に出してよいかの確認 | レポートと図を保存する前に、載せてよい粒度をユーザーに確かめる。規約に確認の相手（クライアントの担当者など）があれば、その確認を済ませたかを聞く |
| 他の成果物 | 上書きせず、新しい日付のファイルで並べる |
| 共有前の理解の確認 | `understand` を勧める（規約が必須にしていれば必須） |

## Step 1: 一次ソースを読む

読む順番:

1. notebook のまとめ表
2. 各「問い N への回答」
3. その問いの根拠になっている図表
4. 補助分析や探索の出力

- まとめ表が無いときだけ、各回答から組み立てる。途中の出力や図だけを見て結論を作らない
- 出力は実行した結果から読む。marimo なら、書く前に `analysis-notebook` の手順（`export session --force-overwrite`）で再実行し、`analysis-notebook/scripts/read_session.py` で読む。古い出力のまま書かない
- 数値は実行の結果から引く。notebook の説明文やコードのコメントに残った概数を出典にしない

## Step 2: 構成を決める

章立ては読み手の型の references に従う。どちらの型にも次を入れる。

- **問いごとの結果**: 問い／回答／根拠／限界
- **総合解釈**:
  - 問い同士の関係
  - 何が言えて、何がまだ言えないか
  - 結果が上位の問い（判断・研究の目的）にとって何を意味するか（数値の再掲でなく解釈）
  - その解釈と競合する説明（交絡・データの偏り・手法の仮定）の検討
  - 結果から次に立てる問い
- **次アクション**: notebook が提案した次の確認事項
- **再現情報**（末尾に短く）: notebook のパス、データを確かめた日、図のパス

1 レポートで共有・確認したいことは 1 つに絞る（1 論点主義）。論点が複数あれば分ける。

## 記述の決まり

- 回答は `問い / 回答 / 根拠 / 限界` を基本形にする
- 未解決の問いは「未解決」と書く。「部分的」を YES に丸めない
- 補助分析は、確度や解釈にどう寄与するかを 1 文で書く
- **コードの内部の語をそのまま本文に出さない**。変数名・状態名は、何が起きているかを日本語で言い換える。どうしても要るなら初出で定義する
- **進行管理の語を本文に書かない**。決定日、会議への言及、「宿題」「積み残し」「前回のご指摘への回答」は作業の層に属する。問われた点は、答えを事実として本文に溶かして書き、「ご質問への回答です」と断らない
- **口語的・比喩的な語を使わない**。中立的な語を選ぶ
- **用語を本文・図の凡例・表のキャプションでそろえる**。図は notebook 側にあるので、本文だけ直して図が古いまま、を起こさない
- **作業の層と共有の層を分ける**。出所・理解度のタグや未消化の点の棚卸しはレポートに出さない。AI が補った導出・主張を確定として書かず、未消化の部分は「要確認」として扱う
- **定型の構造を避ける**。確認したいことは本文に入れてよいが、機械的な見出しや定型の箱にせず、地の文に溶かす。過剰な見出し・全項目同型の表・冗長な前置きを避ける
- **付録は必須にしない**。作る場合も本文だけで完結させ、「付録に回す」「詳細は付録 B に」で本文の話を中断しない

## 事実の裏取り（本文に書く前に確かめる）

固有名詞・件数・定数は、書く前に一次ソースに当てる。推測で埋めない。

- **外部データは初出で正式名称を書く**。略語を推測で展開しない。元データのファイル名・同じリポジトリの過去のレポート・一次資料と照らしてから書く。調査なら実施回・年・対象まで添える
- **母数・件数は実数で書く**。「約 4,000 件」のように丸めない。数え方が複数ある（全体／除外後／集計に寄与した分）ときは、どれを指すかを明示し、必要なら内訳を並べる
- **結果に効く定数（重み・閾値・正規化など）は、出所と役割を 1 文で書けるまで調べてから本文に出す**。既定値のまま・前の版からの引き継ぎなら、そう書く。書けないものを本文に出さない

## 持ち出しのガード（書く前と保存の前）

レポートは notebook の外なので、Step 0 の規約に従って次を確かめる。

- 個人の行、自由記述の原文、コードに書いてはいけない値（ID・個人を指す値・規約が足す値）が、本文・表・図に入っていないか。入っていれば分類・集計に言い換える
- 人数の少ない区分の集計値が入っていないか。入っていれば、載せてよいかをユーザーに確かめる
- 載せてよい粒度を確かめたか（規約に確認の相手があれば、その確認を済ませたか）

## 図の扱い

- 図は「その問いの根拠になっている図」だけを載せる。根拠にならない探索の図は並べない
- 図の直前に、その図がどの問いに効くかを書く
- 図には、可視化の目的・計算の仕方・わかったことを添える。横軸・縦軸が何か、集約の仕方（平均か重み付きか等）を本文かキャプションに書き、その図から何が言えるかを 1〜2 文で書く。図を貼るだけ・キャプションが題名だけ、にしない
- 参照は `![キャプション](相対パス)` にそろえる（`docx-export` がこの形を読む）
- 図は notebook の中で png に書き出す（書き方は `analysis-notebook` の形式の references）

## Step 3: 保存と仕上げ

- 置き場・名前・frontmatter は Step 0 の規約に従う。他の成果物は上書きせず、新しい日付のファイルで並べる
- 規約に検査のコマンドがあれば通す。git の運用も規約に従う
- 共有の前に `understand` で、本文の各主張をユーザーが自分の言葉で説明できるかを確かめるよう勧める。説明できない記述は本文から外す（カットを優先する）。なぜ未解決かを説明できる論点は残してよい
- docx や Google Docs で渡すときは `docx-export` を案内する

## チェックリスト

- [ ] notebook のまとめ表とレポートの結論が一致しているか（再実行した出力から書いたか）
- [ ] 各問いに `回答 / 根拠 / 限界` がそろっているか
- [ ] 未解決の問いを解決済みに見せていないか
- [ ] 図が問いの根拠として説明されているか（目的・軸・計算の仕方・わかったことが添えてあるか）
- [ ] 共有・確認したいことが 1 つに絞られているか
- [ ] 本文の各主張を自分の言葉で説明できるか（説明できないものはカット）
- [ ] 定型の構造になっていないか（確認したい点は地の文に溶けているか）
- [ ] 考察が数値の再掲で終わっていないか（上位の問いへの意味・競合する説明・次の問いが入っているか）
- [ ] 見出し・要旨の指標がすべて定義済みか（読者が本文だけで、その数字が何かを分かるか）
- [ ] 記号が一意か（1 記号 = 1 対象）
- [ ] 入力の件数と出力の件数が突き合うか（途中で変わるなら差分の内訳を 1 行で書いたか）
- [ ] 件数・母数が実数で書かれているか（全体／除外後／集計に寄与した分のどれかを明示したか）
- [ ] 外部データの正式名称を一次ソースと照らしたか
- [ ] 結果に効く定数を、出所と役割まで書けているか
- [ ] コードの内部の語が未定義のまま本文に出ていないか
- [ ] 本文が付録なしで完結しているか
- [ ] 進行管理の語が本文に残っていないか
- [ ] 用語が本文・図の凡例・表のキャプションで一致しているか
- [ ] まとめが「やったこと → 結果」中心か（限界の羅列で膨らんでいないか）
- [ ] 要旨が限界も運んでいるか（良い知らせだけに寄せない。目標に届かない指標は率直に書く）
- [ ] 持ち出しのガードを通したか（個人の行・自由記述の原文・少人数の区分・載せてよい粒度）
- [ ] 読み手の型の references のチェックを通したか
