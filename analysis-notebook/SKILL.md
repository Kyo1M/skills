# analysis-notebook — 問い駆動の分析 notebook

分析の notebook を、問いの定義から実行・結論の整理まで一気通貫で進める。集計を並べて終わりにせず、各問いに答え、答えられないことは答えられないと書く。

何を見るか・どの順で見るかの計画（目的・指標の定義・現状把握・仮説検証）は `analysis-plan` で先に作る。計画があれば、その現状把握・仮説の行を問いにする。レポートにするときは `analysis-report`、結論を人に説明する前に理解を確かめるときは `understand` を使う。

## 使い方

```
/analysis-notebook [分析テーマ / 問い / 既存の notebook のパス]
```

## 入力のモード

- **新規作成**: 新しい問いに対して notebook をゼロから作る
- **既存 notebook の改修**: 既存の notebook を読み、問いと結論のずれを直す
- **既存の結果の読み直し**: 既存の notebook の出力を読み、問いへの回答と限界を組み立て直す

既存の notebook のパスが与えられたら改修を優先し、既存の問い・用語・出力を監査してから書き換える。

## Step 0: 規約を読む（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指すガイド（分析環境の README など）を読み、次を決める。規約に明示があればそれに従い、無ければ既定を使う。

| 項目 | 既定（規約に無いとき） |
|---|---|
| notebook の形式 | marimo。形式に合う references を読む（marimo → `references/marimo.md`、スクリプトを書いて notebook に変換する形式 → `references/jupytext.md`） |
| 言語・実行環境・実行のコマンド | 形式の references の既定。前置き（`uv run` など）やコンテナは規約から読む |
| notebook の置き場・名前の付け方 | `notebooks/<snake_case>.py` |
| データの読み方 | 決まり無し。規約に読み込み関数（例: `load_table("<slug>")`）の指定があれば、それ以外でデータを読まない |
| コードに書いてはいけない値 | ID・個人を指す値はコードに書かない。規約が足す値（店舗名・特定の絞り込み条件など）も書かない |
| notebook の説明文に書いてよい数値 | 集計した値を書く（個人の値は書かない）。計算した値を差し込み、手で書き写さない |
| 個人の行・自由記述の原文 | notebook の出力では展開してよい。notebook の外（説明文・レポート・メモ・図・資料）には出さない |
| 図の文字の制約 | 無し |
| git の運用 | 規約に従う。無ければコミットしない |
| 共有前の理解の確認 | `understand` を勧める（規約が必須にしていれば必須） |

規約が雛形の notebook（`template.py` など）を持っていれば、新規作成はそれをコピーして始める。

## 分析サイクル（固定）

### フェーズ 1: 問い定義

コーディングの前に、次を notebook の冒頭に書く。

- 問い
- 問いごとの仮説
- 判定単位（個人／店舗／月／世帯 など）
- YES／NO／部分的 の判断基準
- 曖昧なラベルの operational definition（例: 「退職者」が期間内に退職日がある人か、在籍フラグが落ちた人か）

問いが曖昧なままコードを書かない。解釈が分かれて結論が大きく変わるときだけユーザーに確かめる。

**問いの批判的チェック**（コーディング前に 3〜5 問を自問する）:

- この問いは、どの意思決定・上位の問いに効くか（目的と手段が入れ替わっていないか）
- 仮説は反証可能か（どんな結果が出たら仮説を棄却するかを先に言えるか）
- 先行の notebook・既存の結果と重複・矛盾していないか（関連の notebook を検索して確かめる）
- この分析で答えが出なかったら、次に何を確かめるか
- ユーザーの問い・仮説も鵜呑みにしない。データの有無や既存の結果と合わなければ、コーディング前に指摘して問いの立て直しを提案する

問いの立て方から整理したいときは、先に `grill-me`（アイデア壁打ちモード）を使う。

### フェーズ 2: 最小分析設計

- 各問いに、答えるのに要る最小限の分析ステップだけを設計する
- 各ステップに「どの問いに答えるためか」を書く
- 直接答えない分析は削るか、「補助分析」と明示する
- 件数が少ない論点は、集計だけで終わらせず個別の確認を先に設計する（目安: 20 件以下は原則全件を見る）
- 回答の出力の形を先に決める（例: `YES: 3 店舗。根拠は 12 店舗のうち 3 店舗だけが基準を満たす`）
- 誤解しやすい指標は、「この数値が意味すること／意味しないこと」を 1〜3 行で先に書く

### フェーズ 3: 実装

- 形式の references の書き方で notebook を編集する
- 各問いの最後に必ず回答の型（下記）を置く
- 件数・割合は判定単位とセットで書く（例: `42 人 = 7 店舗`）
- 「候補」「一致率」「高確度」など誤読されやすい表現には、必要なら「読み方の補足」を置く
- 共通の処理は関数にする

### フェーズ 4: 実行・検証

- 形式の references の手順で notebook を最後まで実行し、出力を読む
- 回答検証チェックリスト（下記）で点検する
- 結論が問いに答えていない、数値が空、図が意図どおりでない、のどれかがあれば、直して再実行する。問いに答えられる状態になるまで繰り返す
- データを取り込み直したときも再実行する（古い出力のまま結論を書かない）
- ユーザーへの完了報告は、実行した事実・主要な数値・図の確認結果とセットで行う。実行を省いて目視の確認だけを頼まない

### フェーズ 5: 結論要約

- 各問いへの回答を 1 段落か 1 セルで明示する
- 最後のまとめ表で全問いを一覧にする
- 「言えない」ところを無理に断定しない
- ユーザーへの報告は、要約 → 根拠 → 限界 の順にする
- 結論を共有・レポートにする前に、各結論・数値・手法をユーザー自身が説明できるかを `understand` で確かめるよう勧める。実装を先に進めた場合も、結論にする前にコードと手法の理解を確かめる（「動いたから採用」を結論にしない）

## 回答の型

各問いの最後に置く。

- **回答**: YES／NO／部分的／まだ言えない
- **読み方の補足**: 誤解しやすい指標が何を意味し、何を意味しないか（必要なときだけ）
- **根拠**: 主要な数値 1〜3 個
- **確度**: 高／中／低
- **限界**: 何が未検証か
- **次アクション**: 次に何を確かめるか

## 推奨の notebook 構成

セルの書き方は形式の references に従う。見出しと項目は次のとおり。

```
0. 概要
   - 問い／仮説／判定単位／判断基準／用語の定義
   - データソース、出力先
1. データの読み込みと基礎確認
   - 最小限の読み込みと件数の確認
N. 問い N: [問いの文]
   - この章が答える問い／仮説／分析ステップ
   N.1 [分析ステップ]   このステップが問い N にどう効くか
   N.x 補助分析（必要なときだけ）   直接の回答でなく、解釈や確度にどう効くか
   N.y 問い N への回答   回答の型
まとめ
   | 問い | 回答 | 根拠 | 確度 | 限界 |
```

問いがまだ固まっていない初期の探索に限り、探索モード（問いの章を立てずにデータを眺める）を使ってよい。探索の後は必ず問い駆動の構成に戻す。

## 分析方針: 代表インスタンスの可視化

集計と統計量だけで終わらせず、各章に「代表的な具体例」を 1 件以上置き、どんなデータがどう処理されたかをイメージできるようにする。

- 集計の単位（行／人／店舗／月 など）に合わせて代表例を 1 件以上取り出し、使った列の値を表で並べる
- 冒頭で定数として決めるのは**選ぶ規則**（例: 指標が中央値に最も近い店舗、件数が最も多い月）にする。ID や個人を指す値はコードに書かず、実行時に規則から求める
- 全章で同じ代表例を追うと、話が一貫して読みやすい
- 「この集計値の根拠は、この代表例のこの列」という対応を説明文に書く
- 代表 1 件では偏る論点（極端値・異常値・混在パターン）は、対照の例を足す
- 集計の対象が 20 件以下なら、代表ではなく全件を見る
- 集計表の**注目行**（少数サンプルの行・外れ値の行・結論を左右する行）は、その行に含まれる行を別のセルで展開して見せる。展開した行や自由記述の原文は notebook の出力の中だけで見る。notebook の外に出すときは分類・集計に言い換える（Step 0 の規約に従う）

## 回答検証チェックリスト

- [ ] 各問いに明確な回答のセルがあるか
- [ ] 回答に具体的な数値が入っているか
- [ ] YES／NO／部分的／まだ言えない が明示されているか
- [ ] 誤解しやすい指標に「何を意味するか／何を意味しないか」の補足があるか
- [ ] 件数の単位が一貫しているか
- [ ] 少数件数（目安 20 件以下）を集計だけで済ませず、全件を確かめたか
- [ ] ラベルや用語の意味を説明文に書いているか
- [ ] 結論が実行した出力と矛盾していないか
- [ ] 直接答えない分析が補助分析として区別されているか
- [ ] 無駄な分析が残っていないか
- [ ] 各章に代表インスタンスの具体値が表示されているか
- [ ] 集計表の注目行（少数サンプル・結論を左右する行）を行の単位で展開したか

## 命名と解釈のガード

- 曖昧なラベルは、何を指すかを定義してから使う（例: 「候補」がどの段階の候補か）
- 「高確度」を使うなら、その条件を先に並べる
- 直接の根拠が無ければ「部分的」か「まだ言えない」を使う
- 支持的な分析結果は「答え」ではなく「補助根拠」として扱う

## 実装の決まり

- 共通の処理は関数にする。変数・関数名は `lower_snake_case`
- コメントは日本語で意図を書く
- 図の軸ラベル・凡例・タイトルを必ず付け、切れないようにする。図は単体で、軸・凡例・キャプションから意味が分かるようにする。規約に図の文字の制約があれば従う
- 抽象的な指標・概念は、実数や分布の図で見せる（スカラーの要約だけで済ませない）
- パスや重要なパラメータには理由を添える
- 同じ指標の組の相関は、notebook をまたいで同じ方法（順位か値か、対象の代表値は平均か中央値か）にする。違う方法を使うときは説明文に書く
- 比率の指標（予算達成率など）には、水準の指標（売上そのもの・席あたりなど）を並べて出す。グループがそろって動く推移には、全体のその月の値を引いた版も出す
- 図の説明文（色・凡例の読み方）は、書き出した png を開いて確かめてから書く
- データは規約の読み方でだけ読む。コードに書いてはいけない値を書かない

## 補助

- 大きな分析では、既存の notebook の監査や結論のレビューにサブエージェントを使ってよい。ただし主担当は 1 つに保ち、最終の結論の責任を分けない
