# Deck Outline — 資料構成を実文言 md で設計する

スライド・提案資料・定例デッキなどを作るとき、**実装（HTML / デザインツール）に入る前に「構成」を実文言の Markdown で固める**ためのスキル。

## なぜ構成を md で分離するのか

スライド作成は、見た目や実装に気を取られると中身の構造がぼやける。さらに HTML を直接書き始めると「構成のレビュー」と「実装の手戻り」が混ざり、章立てや主張のズレを直すコストが跳ね上がる。

このスキルは構成を**実装ツールに依存しない中間成果物**として切り出す：

- 構成 md は人がそのまま読んでレビューできる（タイトル・リード文・ボディが実文言）。意図の言い換え（「〜のねらい」）だけだと、スライドの中身が想像できずレビューにならない。
- 同じ md を html-slide-deck（HTML）にも Claude Design にも渡せる（ツール非依存の引き渡し）。
- 論理の軸を先に通すので、表紙の目的と各ページの主張が繋がる。

**このスキルは実装には進まない。** ゴールは「レビュー済みの構成 md」と「次の実装ステップへの引き渡し」まで。HTML 生成やデザインは html-slide-deck / Claude Design の役割。

## 初稿で適用する文章ルール

日本語の業務スライドは、構成・実文言を書き始める前に `~/.codex/skills/business-slide-writing/references/principles.md` を読む。共有する対象と相談事項を先に定め、概要には利用状況・機能・作業を載せる。管理履歴を機械的に転載せず、指定された内容・必要な制約は維持する。表や役割欄は対象と作業が分かる自然な名詞句を使える。共通ルールは文章と情報選択に適用し、過去の担当・日程・状態を引き継ぐ根拠にしない。

## ワークフロー

```
Phase 1 コンテキスト把握＆規約検出
  ↓
Phase 2 資料の狙いを一文で決める
  ↓
Phase 3 章立て・役割設計
  ↓
Phase 4 実文言ドラフト
  ↓
Phase 5 トレーサビリティ＆一貫性点検
  ↓
Phase 6 保存・レビュー gate・引き渡し
```

Phase 2 と Phase 5 を飛ばさない。ここが「目的と中身が繋がらない資料」を防ぐ核心。

### Phase 1: コンテキスト把握＆規約検出

- **素材を読む**: 依頼内容、関連する議事録・フィードバック・決定事項、改訂なら既存版（流用できる部品＝図表・章・言い回しを把握する）。
- **リポジトリ規約を検出する**: その repo の `CLAUDE.md` / `AGENTS.md` から、**出力先ディレクトリ・命名規約・frontmatter スキーマ・lint・git 運用**を読み取る。特定のディレクトリ構造をハードコードせず、その repo の規約に従う（規約が無ければ `docs/` 直下や会話内提示にフォールバック）。
- **読者・目的・ボリューム感・前提知識を掴む**。提示されていなければ対話で引き出す（1 問ずつ。多問を一度に投げない）。
- **言われたことをそのまま実行するのではなく、批判的に意見・質問を返す**。素材（過去の議事録・決定事項・依頼者の発言）に、ページ構成や圧縮の判断に影響する具体的なアイデア・数値・チェック項目があれば、それを本当に落としてよいか確認する。既存の正式決定（ADR 等）と矛盾する変更をしようとしている場合は、それを明示して依頼者の判断を仰ぐ。「言われた通りに整える」ではなく「より良い資料にするための壁打ち相手」として振る舞う。
- **入力メモのインベントリ化**: 依頼者のアイデアメモ・走り書き・会話中の発言を、**項目単位の番号付きリスト**（M1, M2, …）に起こす。フィードバック・決定事項だけでなく、依頼者が書いた素のメモこそ黙って省略されやすい。このインベントリは Phase 5 のトレーサビリティ表の「出所」に必ず含め、全項目の反映先を突合できる状態を作る。

### Phase 2: 資料の狙いを一文で決める

資料全体を貫く主張を **1 文**で書く。表紙の目的と、各ページのユースケース・主張を、この一文にぶら下げる。背景 → 課題 → 解決 → 具体、の因果が一本で通るかを確認する。

狙いが決まらないまま章立てに進まない。「目的（表紙）と具体（各ページ）が繋がっていない」という最頻の指摘は、ここで狙いを先に通すことでしか防げない。

例: 「プロジェクトの品質は“文脈”で決まる。だから対話型 AI でなく文脈を管理できる仕組みを使い、セルフレビューと文脈共有で品質を底上げする。」

狙いを書いたら、その下に「ページの流れ」（どのページで何を示し、次にどう繋ぐか）を矢印で 1 段落にしておく。節の見出しは「この資料で伝えたいこと」「ページの流れ」のような普通の語にし、「因果チェーン」「背骨」のような独自の言い方をしない（2026-08-26 FB: 「因果チェーンという言い方はよくわからない」。実例は `references/tone-examples.md`）。

### Phase 3: 章立て・役割設計

- 狙いの因果に沿って章を並べる。
- 各スライドに**役割**を与える。意思決定の場の資料（定例・部会・レビュー会）なら 報告／確認／議論／参考 ＋想定時間。説明・ハンズオン資料なら 導入／本論／実践／まとめ 等。
- **【議論】タグのスライドは 1 論点に絞り、聞きたいことはリード文に畳む**: 方針（たたき、具体を伴う）をボディで示し、確認・相談したいことは独立した「問い」「この場で決めたいこと」欄を立てず、**リード文の末尾に改行して 1〜2 文で添える**（html-slide-deck の Pattern 14 と揃える。2026-07-09 追記: 毎スライドに問い欄が並ぶとしつこいという FB を受け、question-decision 型の独立ブロックを廃止した）。現状・たたき・仕組み・オープン論点を無秩序に同居させない — **1 ページ 1 決定**が原則。あぶれた要素は【参考】ページかまとめの持ち帰り論点（パーキングロット）へ送る。**議論が「切り分け」と「作り方」の 2 段になるときは 2 枚に分ける** — 「この分け方でよいか」と「この手順でよいか」は別の問いで、1 枚に同居させると手順の細部に目が行き、分け方への合意が取れないまま進む。切り分けページは表 1 つだけでもよい（`references/writing-principles.md` 原則 22）。
- **既定は方針（たたき）の直接提示。選択肢の並列比較はユーザーが明示的に依頼した場合のみ** — 「A案／B案／C案から選んでください」と丸投げしない。推進側の考えを、判断に迷う点は推奨として添えつつ直接示し、それをもとに議論する。比較が要ると明示された場合だけ、選択肢 2〜3・判断基準（3 つまで）を足す（2026-07-01 追記：初回実運用で「複数案の比較より方針と具体案を直接示してほしい」という FB を受け、既定を反転した）。
- **圧縮のために具体性を落とさない** — 1 ページ 1 決定・簡潔さを優先するあまり、依頼者が既に示した具体（チェック項目・数値・手順・固有名詞）を一行の抽象ラベルに縮めない。方針（たたき）の中身は、読み手がその場で妥当性を判断できるだけの具体を残す。削るかどうか迷ったら黙って削らず、依頼者に確認する。
- **定例までに実施予定のイベントは実績報告ページとして設計する** — 構成時点で「今週実施」の予定でも、資料提示までに実施済みになる見込みなら、予定の紹介でなく実績報告（日時・参加者・合意したこと・現状・出た論点）のページとして枠を取る。逆に、未着手の「次の整備」構想は独立ページを立てず、スケジュール表の 1 行に畳む。スケジュールはトラックが分かれても 1 枚の週次ガントに統合する（`references/writing-principles.md` 原則 18〜20）。未着手の構想は、スケジュール表の 1 行のほか、その整備が必要になった文脈のページの隅に添えてもよい。進まなかった項目は枠を消さず「進行中」「残タスク」等の短い状態ラベルで残す（遅れた理由は添えない）。
- **対象の工程・構造の全体像を【再掲】として 1 枚置く** — 工程番号を最初に使うページの手前に置く（仕組みの説明が議論より先なら、その前。議論の直前とは限らない）。空ページ＋流用元（ファイル名・ページ番号）だけを書き、作り直さない。ロードマップ（どこまで行くか）とは別物で、ロードマップだけでは「本日の議論が全体のどこの話か」が伝わらない（`references/writing-principles.md` 原則 21・38）。
- **依頼者のメモの型を勝手に変えない** — 「タスクを洗い出したい」を「順番の初期値」に置き換えるような型の変換は、理由があっても黙って行わない。変えたい案は並記して選んでもらう（2026-08-26 FB。`references/writing-principles.md` 原則 37）。
- **取り組みの軸の名前を固定する** — 「①仕組みの実装」「②運用・定着支援」のような番号付きの軸名を、目次・ページタイトル（「①仕組みの実装：検証・テスト」）・テーマ表・ガントのトラック・まとめで同じまま使う。ページごとに言い換えない（`references/writing-principles.md` 原則 41）。複数の仕組みを報告するときは全体像の工程順に並べる（原則 45）。
- **議論用のテーマ表は「軸／テーマ／優先度（高・中・低）」を基本に、分担も相談する回は「担当（案／仮）」を足す** — 優先度を時期で書かず、時期はスケジュール表で優先度が決まってから置く。現在地の列と、推進側の内部整備・すでに運用に乗ったものの定着・時期未定の構想は載せない（原則 47）。1 人との会話で出た論点は独立の議論ページにせず、テーマ表の 1 行＋リード文の一言に畳む（原則 48）。
- **まとめは「今後」が主役** — 本日の共有 3 行・今後は時期を頭に 3〜5 行。「お伺いしたいこと」「前回決めたこと」の枠は要る回だけ置き、無い回は該当ページのリード文で聞く（原則 49）。
- **「本日の論点」のような一覧ページを立てない** — 議論はテーマのページ（タスク整理・切り分け等）で行い、聞くだけのことはまとめの「お伺いしたいこと」に置く（原則 37）。
- **決めないと決めた議題は【確認】でなく【参考】に落とす** — 網羅表 1 枚に畳み、実際に見るものを色で示す（絞り込みを別カードにして本編と Appendix に分けない）。新しい分類を持ち込まず、既に共有されている軸に乗せる。締めに「いつ相談し直すか」を一文置く（`references/writing-principles.md` 原則 23）。
- **時期・数値は伏せずに仮置きで出す** — 触れたくない含意（体制・契約等）があっても、遠い将来の目標時期を空欄や「その先」にすると、相手がそこを埋めようとして議論が発散する（`references/writing-principles.md` 原則 24）。
- **「まとめ」ページは必ず置く。「今後」ページは任意で添える**（説明・提案・ハンズオンなど締めのある資料）。まとめには本論の振り返りと持ち帰り（次に何をするか）を入れる。今後（発展・運用の次の一歩）は、内容が単体で完結していれば省略してよい。**締めページを重複させない** — 「振り返り」と「まとめ」を別ページに分けず 1 枚に畳む。
- 改訂でも各スライドに 🆕/✏️/♻️ の区分バッジを付けない（構成 md は単体で完結させ、前版との差分を追跡しない。差分は git に残る。2026-08-26 FB）。流用するページだけ「流用元（ファイル名・ページ番号）」を書き、それ以外は空ページにする（作り手が元 pptx から手でコピーする。概要や差し替え箇所は書かない）。**読者向けの本文・スライドにも前版との差分を持ち込まない**（Phase 4 の「単体で完結」を参照）。
- **機能の出力や動作を説明する報告ページには実物を置く** — 仕組み・案件の報告は、作ったもの・動いたもののスクショ（出力ファイル・設計書・PR 一覧・リポジトリの画面）を 1〜2 枚置く前提で枠を取り、本文はその読み方と結果に絞る。画面共有は補助（pptx に残らず、後から読む人に伝わらない）。画像生成の挿絵は進捗を伝えないので置かない。全体像テーブルに「実物」列（枚数）を持ち、0 枚の報告ページには理由を書く（`references/writing-principles.md` 原則 39。2026-08-26 FB: 「実施内容や今後は書いてあるが具体的なアウトプットが見えないので、進んでいるように見えない」）。
- **全体像をテーブルで一覧化**（章・スライド・役割・実物・目安）。ここで枚数とボリュームのバランスを点検する。

### Phase 4: 実文言ドラフト

各スライドを、**そのまま載せる前提の実文言**で書く。意図の言い換えで止めない。最低限：

- **eyebrow**（小見出し・英語ラベル等）
- **タイトル**（体言止め・名詞句を基本に。動詞締めは避ける）
- **リード文**（結論＋判断理由・結果を 1〜3 行、動詞で締めてよい。結論だけの 1 文に切り詰めず、ボディの縮約にもしない）。**短い文の連打にしない** — 細切れの一文を並べると機械的（AI っぽい）に映る。1 文が 2〜3 行とやや長くなってもよいので、接続詞でつないで自然な流れの文章にする。ビジネス資料では「今日」→「本日」のように改まった語を選ぶ（リポジトリの読者配慮トーンに合わせる）。**「前回ご指摘をいただきましたので」のような、そのページを作った経緯を書かない** — 経緯は【振り返り】ページの宿題表で済んでおり、各ページで繰り返すと同じ話を人数分読ませることになる。リード文はボディの要約にはしない（`references/writing-principles.md` 原則 8）。
- **ボディ**（実際の中身：箇条書きの文言、カードの見出しと項目、表の行、チャット例・コード例・before/after の実テキスト）。**箇条書きで体言（単語）を羅列しない** — 「掴む／試す／決める」のような単語並べは機械的に映る。各項目を短い文 1〜2 行で書き、補足は子の箇条書き（2 階層まで）で足す（例「議事録作成とクエリレビューを実際に手を動かして試す」）。ラベル＋説明形式のカード見出しは可。**「太字キーワード ── 説明」の 1 行圧縮と `──`・`―`・`—`（長いダッシュ類）は使わない** — 見出しが要る項目は「太字の見出し行＋次行から本文」か「見出し：本文」（全角コロン）で書く。タイトルにも副題の `──` を付けない。
- **図版指示**（**何を置くか**を書く：html-slide-deck の型の名前（進行表／4 ステップ／提供価値 3 軸／ガント／比較表／進捗報告／議論／箇条書き型 など `html-slide-deck/references/slide-patterns.md` §0 の名称）と、**アイコンを付ける概念名**（`html-slide-deck/references/icons.md` の対応表の語。カード見出し・工程ノード・行グループ名のどれに付けるか）。**どう実装するか**＝CSS やコンポーネントは実装スキルに委ねる。文字だけの枚なら「箇条書き型」と書いてよい）
- **スクショ（実物）**（機能の出力や動作を説明するページは原則あり。利用状況の横断一覧など、画面が主張を補わないページは無理に追加しない。番号を付けて、何の画面か・どの状態か・写す範囲（トリミング）・比率（画面全体や表は 16:9、一覧やツリーの横長は 8:3）・置き場所・キャプション 1 行・ファイル名（repo の資産ディレクトリに `sN-shotM-<slug>.png`）・写してよい範囲（顧客名・実データ・個人名の扱い）を書く。無いページは「なし」と理由を書く。撮影の一覧は TODO 節にまとめる）
- **補足**（任意：画面共有で見せるもの、流用元。前版からの変更点や制作の経緯は書かない）。画面共有は実物のスクショを置いたうえでの補助にする（聞かれたら開くもの）。実演が主のページだけ、役割バッジと並べて**「画面共有」バッジ**を付ける（これは読者向けに表示してよい）

抽象スライド（仕組み・概念・アプローチ）には、具体イメージ（コード例・ディレクトリツリー・観点リスト・擬似 UI）を隣接させるか本文に小さく内包する。抽象単体では「で、結局何をどう作るのか」が届かない。

**実文言で必ず守ること**（2026-08-26 FB。詳細は `references/writing-principles.md` 原則 33〜38）:
- 工程・フローの各ステップに主体（ヒト／AI）を付ける。誰がやるかが無いと「レビューするのは AI か」と聞かれる。
- 段階に合った断定度で書く。たたき・検証中のものを「〜する仕組みです」と言い切らず「〜する仕組みのたたきを作成し、動作確認しました」。仕組みのページのリード文は「作ったもの＋それで何がどう良くなる（見込み）か」で締め、手順の細部（実データ確認の条件等）はボディへ。
- 読み手から来そうな疑問（「ダミーデータで意味があるのか」）は 1 行の注釈で先回りし、未検証なら「〜で確かめる」と書く。構想段階の次の一歩は括弧書きで添える。
- レビュー反映は「週次でお見せし、フィードバックをもとに修正した」の 1 文にする。誰の何の指摘をどう直したかの表は置かず、リード文に個人名付きの指摘を書かない（詳細は議事録が正本）。
- 報告ページは前回の定例で話した状態からの変化点（例: クエリレビューが Teams のチャットから PR に変わった）を先に書く。
- タイトルは対象を名指す短い名詞句（「分析設計」「追加・その他の運用支援」）。「A から B まで」の範囲表現や「広がり」のような抽象語を避ける。製品名は正式名で統一し略さない（「Copilot」→「GitHub Copilot」）。
- 資料化の直前に更新する箇所は「（TODO: …）」で書く（〔 〕は目に付きにくい）。
- 機能の出力や動作を説明する報告ページは実物のスクショ 1〜2 枚＋読み方と結果で組む。概要一覧に読めない画面を添えるためだけの実物枠は設けない。リード文 2〜3 行、箇条書き 1 項目 1 行（全角 45 字以内）、表のセル 2 行以内、フロー図の文字は工程名＋主体＋1 短句まで。落とした細部は「口頭で補足すること」へ移し、移した項目はレビューの返答で一覧にして承認を得る（原則 10 と 39 の両立）。
- 読み手に自明なことは書かない。相手が知っている人の肩書き・所属・チーム人数、相手自身からの依頼の経緯、他ページにある実施日の再掲は載せず、カードの見出しは名前だけにする（原則 40）。
- 仕組みのリード文の目的は、相手が得る価値（「クエリの間違いや集計ミスを書いた時点で検知し、集計の品質を上げる」）で書き、作り手の検査観点を目的に置かない（原則 43）。資料化までに終わるか不確かな作業は「できたこと／これから」の 2 段にし、リード文の締めは到達点の候補ごとに「（TODO: …）」を用意する（原則 44）。
- 案件ページは進行表（状態）＋「今週実施したこと／今後の予定」の 2 列（動き）で組む（原則 46）。
- 飾りを置かない: 英字 kicker（表紙も）・アイコン（既定は全ページ 0 個）・進行表の凡例（原則 42）。図版指示の「アイコンを付ける概念名」は、依頼があるときだけ書く。

**成果物も構成 md も単体で完結させる。** その資料だけを読んで理解できる構成にし、前版（v1・v2 …）との差分や「前回はこうだった」を本文・スライドに持ち込まない。構成 md にも「前版からの変更点」の節を置かない（差分は git のコミットに残る）。

### Phase 5: トレーサビリティ＆一貫性点検

- **トレーサビリティの突合**: フィードバック・決定事項・要件、および **Phase 1 で作った入力メモインベントリ（M1, M2, …）の全項目**が、どのスライドで反映されたかを突合する（出所 → 内容 → 反映先スライド#）。**結果は構成 md に書かず、レビューの返答（会話）で示す**（2026-08-26 FB: 「トレーサビリティなどはこのドキュメントにそもそも必要か」。md に残すと読み手が本文に辿り着く前に制作メモを読まされる）。
- **落とす項目の明示承認**: 反映先が無い項目は黙って落とさず、「意図的に落とす提案」として会話で一覧提示し、承認を得る。タイトル・リード文への反映で足りる項目は、その旨を添える。
- **一貫性チェック（このスキルの肝）**: 各スライドが狙い（Phase 2 の一文）に繋がるかを 1 枚ずつ確認する。表紙の目的と各ユースケース・主張が直結しているか。繋がらないスライドは、主張を書き換える／狙い側を見直す／削る、のいずれかで必ず解消する。**唐突な対比軸を入れない** — 狙いにぶら下がらない切り口（例：品質の話の中に突然出てくる「自分が速くなる」）は、前後の文脈なく置くと浮く。狙いに沿った軸へ言い換えるか、落とす。
- **自然な日本語チェック**: 声に出して読み、実際に打ち合わせでコンサルタントが言う言い回しになっているかを確認する。Phase 4 のタイトル規範（体言止め・動詞締め回避）が全スライドで守れているかを再確認し、比喩的な独自ジャーゴンを見出しに使っていないか（例：「背骨」）、抽象的な体言化で内容が空疎になっていないか（例：「〜という到達点」）、「だから」の多段連鎖で因果を並べていないかを見る。迷ったら `references/tone-examples.md` の Before/After と照らす。
- **プレースホルダ走査**: TBD・空欄・曖昧な要件が残っていないか。残っていれば埋めるか、Phase 7 のオープン論点へ明示的に上げる。

### Phase 6: 保存・レビュー gate・引き渡し

- Phase 1 で検出した規約に沿って md を保存する（壁打ち・設計の成果なら exploration 系、確定構成なら deliverable の前段など、repo の慣習に合わせる）。frontmatter を付け、lint があれば通す。git 運用ルールがあれば従う（ブランチ・コミット確認等）。
- **鮮度チェック**: 構成 md の承認から資料提示までに日が空く場合、引き渡し・資料化の直前に「予定として書いた項目が実施済みになっていないか」（直近の議事録・イベント）を確認し、該当があれば実績報告へ更新する（`references/writing-principles.md` 原則 20）。
- **レビュー gate**: 「構成 md を `<path>` に保存しました。実装前にレビューをお願いします」とユーザーに渡し、**待つ**。修正依頼があれば Phase 3〜5 を回す。
- **引き渡し**: 承認後、次の実装ステップを 2 択で提示する：
  - **HTML 化** → `html-slide-deck` スキル（構成 md を入力に、型の選択・`.dc.html` 実装から始める。pptx が要るときは生成した `.dc.html` を Claude Design に持ち込む）
  - **Claude Design に直接** → 同じ md をデザインのブリーフとして渡す（html-slide-deck の持ち込みが使えないときの代替）
- 実装後の仕上げ確認には `deck-critique` スキル（別の目での批評・推敲）が使える。構成 md とメモインベントリを一緒に渡すと脱落突合まで検査される。

## 出力フォーマット

構成 md の標準構成（伝えたいこと＋ページの流れ／全体像テーブル／実文言／口頭で補足すること／TODO／確認したいこと）と実文言の粒度は `references/output-template.md` を参照。汎用の最小例も同梱している。自然な日本語チェックで迷ったら `references/tone-examples.md` の Before/After 実例を参照。

## 適用範囲

スライドに限らず、章立てと主張の一貫性が要る資料（提案書・レポート・説明資料）の構成設計に広く使える。実装ツールが HTML でも Claude Design でも PowerPoint でも、構成 md は共通の入力になる。

## このスキルと html-slide-deck の関係

- `deck-outline`（本スキル）＝ **構成**（問いの整理・章立て・実文言 md・一貫性担保）まで。
- `html-slide-deck` ＝ **HTML 実装**（型の選択・事業用スライド DS の適用・`.dc.html` 出力・機械チェックとセルフレビュー）。構成 md を入力に受け取って実装する。口頭補足・守りの理屈は構成 md の「口頭で補足すること」節に残し、デッキには入れない（発表者ノートは使わない）。

「スライドを作りたい」という依頼は、まず本スキルで構成 md を固め、レビュー後に html-slide-deck か Claude Design へ渡す、の順で進める。
