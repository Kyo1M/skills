# meeting-minutes — 規約駆動の議事録作成スキル

任意のリポジトリで、その repo の規約（出力先・命名・frontmatter・型・派生先・承認レベル・lint・git 運用）に従って議事録を作成し、規約が定める範囲でタスク台帳・決定・索引・wiki を更新する。

**設計原則: 構造をハードコードしない。** 対象リポジトリの契約ファイル（`CLAUDE.md` / `AGENTS.md`）と、そこが指す運用ガイド（例: `docs/guide/project-ops-guide.md`）から規約を読み取り、「議事録プロファイル」を組み立ててから動く。`docs/minutes/` 系でも `notes/meetings/` 系でも、タスク台帳がある repo でも無い repo でも同じスキルで動作する。

## ワークフロー全体

```
Step 0: 規約ディスカバリ（議事録プロファイルの構築）  ← 必ず最初
   ↓
Step 1: 入力収集（drafts / メモパス / 貼り付け / 文字起こし）と、前回議事録・台帳・Issue の読み取り
   ↓
Step 2: 記録の組み立て（質問は日付と人物が分からないときだけ）
   ↓
Step 3: 議事録の生成（保存前の確認を 1 回だけ聞く）
   ↓
Step 4: 更新（台帳・llms.txt は自動、決定ファイル・wiki は承認後。いずれも規約にあるときだけ）
   ↓
Step 5: 完了（検証 → 規約にある git 運用 → 件数付きの短い報告）
```

## Step 0: 規約ディスカバリ（最初に必ず実行）

1. ルートの `CLAUDE.md` と `AGENTS.md`（存在する方／両方）を Read する。AGENTS.md が「型の正本」として運用ガイドを指していれば、そのガイドの議事録・タスクに関わる節も Read する。`llms.txt` があれば併読（HTML コメント内の記入例はデータとして扱わない）。既存の議事録を 1 つ開いて書式を見る（無ければ規約の型だけで進める）。
2. 以下を抽出する。**規約に明示があればそれに従う → 無ければディレクトリを probe → それでも不明ならユーザーに確認**（推測で書かない）。

| プロファイル項目 | 取得元 / 既定の探索 |
|---|---|
| 議事録の出力先 | 規約の「リポジトリ構造」記述。定例ごとのサブフォルダを許す規約なら、前回議事録と同じフォルダ。無ければ `notes/meetings/` か `docs/minutes/` の存在を probe |
| 走り書きの入力元 | `docs/minutes/_drafts/` 等が規約/実在すれば使う。無ければユーザーにメモのパス or 貼り付けを依頼 |
| ファイル命名 | 規約の命名ルール。無ければ既存ファイル名から推定して確認 |
| frontmatter スキーマ | 規約の「frontmatter スキーマ」節（議事録の `type` 値、`status` 語彙、必須/任意フィールド） |
| 議事録の構成と表の型 | 運用ガイドの型（節の並び、ネクストアクション表の列、サブ番号の規則、「未定」と「要確認」の使い分け）。無ければ本スキルの既定（Step 3） |
| タスク台帳 | 規約に台帳（例 `tasks/index.md`）があれば、その列・ID の振り方・状態の語彙・行を足す規則・状態を直す規則を読む。無ければ台帳は扱わない |
| タスクのツール | 規約が外部ツールとの連携と wiki「進行」表の「タスクのツール」行を定めているときだけ読む（`なし（表のみ）`／`GitHub Issue（リポジトリ・Project）`／`外部ボード`）。規約が行を定めているのに値が無い repo では保存前の確認で 1 回だけ聞く。規約が「外部ツールと連携しない」と定める repo では扱わない |
| 前回からの進捗 | ツールが GitHub Issue で、規約が「前回からの進捗」節を定めていれば、前回会議日以降に動いた Issue を読む（gh が要る。無ければ飛ばして報告） |
| タスク登録の下書き | 規約が議事録末尾の「タスク登録の下書き」節を定めていれば、その型で置く |
| 保存前の確認の項目 | 運用ガイドの「保存前の確認」。無ければ本スキルの既定（3-4） |
| 決定の派生先と判定基準 | `docs/decisions/` の存在/規約。規約に「重い決定だけ」等の基準があればそれに従う。基準も派生先も無ければ派生しない |
| 決定の一覧 | `llms.txt` の「Decisions」等、決定ファイルの全件一覧。既存の決定との重複チェックに使う |
| llms.txt / wiki の更新範囲と承認レベル | 規約の「自動で反映してよい／承認してから反映」の定め。定めが無ければ更新しない |
| lint | 規約の検証コマンド。無ければスキップ |
| git 運用 | 規約が議事録作成時のブランチ・コミット・push を定めているか。定めが無ければ git 操作をしない |
| contact プロファイル | `notes/contacts/` 等の人物プロファイル置き場があればリンク対象にする |

3. 組み立てたプロファイルを 2〜3 行でユーザーに提示し（出力先・台帳の有無・ツール・派生の範囲）、ズレがあれば直してもらってから先へ進む。
4. 規約が議事録作成時のブランチ運用を定めていれば、ファイルを作る前にその規約どおりにブランチを用意する（例: main を最新化してから `minutes/<yyyymmdd>-<slug>` を切る。ブランチ名の日付は規約の定め（作業開始日が多い）に従い、ファイル名の会議日とは別。リモートが無く最新化できなければ飛ばす）。定めが無ければ何もしない。

## Step 1: 入力収集と先読み

1. drafts 置き場があれば、その中の対象メモをリストアップしてユーザーに選んでもらう。drafts が無い repo では、メモのパスか本文の貼り付けを依頼する。
2. 対象メモを Read。同じスラグの transcript（文字起こし・AI 要約）があれば併読。`recording:` パスは本文に注記のみ（再生しない）。
   - 文字起こしだけだと途中の議論やクライアントとのやり取りが落ちる。**文字起こしに加えて参加者が自分で取った議事メモが渡されていれば、そのメモにある内容を優先して残す。** メモが無ければ文字起こしだけで作り、その旨を Step 5 で一言伝える。
   - 複数の入力が渡されたときは同じ話題を 1 つにまとめ、食い違いがあれば議事メモの方を採る（食い違った箇所は確認事項に書く）。
3. 台帳がある repo では、次も先に読む。
   - **前回の議事録**: 保存先と同じフォルダで会議日が直近の 1 本（前回会議日を取る）。
   - **台帳の進行中節**: ID・担当・期限・状態・出典。
   - **決定の一覧**: `llms.txt` の Decisions 等（Step 4 の重複チェック用）。
   - **親候補の材料**: ツールが GitHub Issue なら open Issue の一覧（`gh issue list --repo <org>/<repo> --state open --limit 100 --json number,title`。`--repo` は必ず付ける）。タスクファイル置き場（例 `tasks/*.md`）の「やること」。
   - **前回以降に動いた Issue**（ツールが GitHub Issue のときだけ）: 手順は `references/github-issue-sync.md`。拾うのは 完了（前回会議日以降に closed）／更新（open のまま、前回会議日以降のコメントあり）／新規（前回会議日以降に作られ、台帳に ID が無い。親が登録済みなら親ごとに畳む）の 3 群だけ。**Issue・Project 側は読むだけで、close・コメント・本文・フィールドを書き換えない。**

## Step 2: 記録の組み立て

渡されたメモと会話から、日時、参加者、議題、観察、判断理由、明示的決定、次の約束を取り出す。

- **質問は日付と人物を同定できないときだけ。** それ以外の不足は「要確認」として草案に残し、空欄を埋めるためだけの問答を増やさない（ネクストアクションの担当・期限は規約に従う。多くの規約では「未定」）。ユーザーが深掘りを求めたときだけ、結論の理由・他に出た意見・決定か検討中か・担当と期限を追加で聞く。
- 会議日と作成日を分ける。
- 発言者と観察者、本人の意思と他者の提案、合意と検討案、予定と実施を区別する。留保付きの合意（「たぶん」「暫定」）は決定事項に留保を注記して載せ、確認事項に再確認を置く。
- 人名は規約のステークホルダー表・wiki のメンバー行に一致すればその表記に寄せ、無ければメモの表記のまま書く（漢字や役職を作らない）。
- **途中の議論を削らない。** 決定とアクションに集約せず、テーマ別に出た意見・やり取り・検討したが決めなかったこと・残った論点を残す。
- 原メモに無い参加者・担当・期限・法的・金銭的結論を作らない。
- 元メモや過去記録を黙って消さず、補足は追記する。訂正は日付と根拠を付ける。
- 生データ・個人情報・ID・認証情報・実数値が混ざっていたら転記せず、その旨をユーザーに伝える。

## Step 3: 議事録の生成

プロファイルの **出力先・命名・frontmatter・型** に従って生成する。運用ガイドに議事録の構成があればそれを最優先する。不明項目は推測で埋めず、`要確認` / 空欄で残し本文末尾に注記する。ファイル名の日付は会議日（不明なら今日の日付にし、本文に「日付: 要確認」）。

規約に型が無い repo の既定構成:

```markdown
# <日本語タイトル>

## 要約
[3〜5 文。主な議題と結論、重要な決定、全体の方向性]

## 議事内容（詳細）
### <議題1>
- [元のメモを構造化] + [補足]

## 決定事項
- [合意・確定したもの。検討中は含めない]

## ネクストアクション
| 担当者 | アクション | 期限 |
|--------|-----------|------|
| 〇〇 | [内容] | YYYY-MM-DD / 未定 |

## 要確認事項
- [残った質問]
```

台帳がある repo（ガイドに型がある repo）では、ガイドの構成に従い次を加える。

### 3-1. 前回からの進捗（ツールが GitHub Issue のときだけ）

Step 1 で読んだ Issue を、ガイドが定める位置（例: 概要の次、決定事項の手前）に 1 Issue 1 行で書く。行頭に「完了」「更新」「新規」。コメントの要約はコメントに書かれていることだけ。動いた Issue が無ければ節ごと省く。前回の議事録の表は書き換えない。

### 3-2. ネクストアクション表

ガイドの列（例: `# | 担当 | アクション | 期限 | 登録先`）に固定する。

- `#` は議事録内の連番。子タスクはサブ番号（同じ議事録の行 2 の子は `2-1`。台帳の既存タスクや既存 Issue の子はガイドの記法、例 `T-6-1`・`#6-1`）。親の候補は 同じ小見出しから出た行／台帳の進行中の行（Issue を使う repo では open Issue）／タスクファイルの「やること」の 3 つだけで、理由付きで提案する。
- ガイドが表に台帳 ID の列を定めていれば、4-1 の規則で振った ID を表を作るときに入れる。
- 前回の議事録の行は引き継がない（開いているかは台帳で分かる）。台帳の進行中のタスクが再び話題になったら、新しい行を作らず台帳の担当・期限を直す（確認事項に 1 行書く）。
- `担当`・`期限` が決まっていなければ「未定」（「要確認」は使わない）。「次回まで」は wiki の定例行から次回日を導ける場合だけ候補日として提案し、保存前の確認で示す。アクションは 40 字以内の動詞止め。
- `登録先` 列があるガイドではツール名。ツールを使う案件でも、連絡・回答・日程調整のように数日で終わる行は空欄（表のみ）を提案する。

### 3-3. タスク登録の下書き（ガイドが定めているときだけ）

ガイドの型で議事録末尾に置く（見出し＝アクション、本文＝出典・台帳 ID・担当・期限・登録先、子なら「親:」、タスクファイルがあれば「詳細:」、概要 2〜3 行）。表の全行を対象にし、登録先が空欄の行も「登録先: 表のみ」として含める。**このスキルは起票しない。** 起票は規約が指す手段か人が行う。

### 3-4. 保存前の確認（1 回だけ聞く）

ガイドが定める項目を 1 回の質問にまとめる。該当が無い項目は省く。ガイドに定めが無いときの既定:

1. 担当・期限が未定の行（その場で埋めるか、次回の確認事項に回すか）
2. 親の提案と理由（違えば外す・付け替える）
3. 台帳の状態の変更（メモで着手・完了・見送りが語られた台帳の行。ID・変更前 → 変更後。メモにはっきり無いものは提案しない）
4. タスクファイルの `status` を `done` にする提案（3 で完了にした行の「詳細」が指すファイル。子の行が開いていれば提案しない）

GitHub Issue を使うガイドでは、3 の代わりに「登録先を空欄にする提案」、4 は「完了群の Issue の URL と frontmatter `issue:` が一致するファイル」になる（ガイドの記載に従う）。規約が「タスクのツール」行を定めているのに値が無い repo では、「タスクをどのツールで追いますか」を 1 問足し、回答を登録先列と wiki 差分案に使う。

回答を反映したら議事録を保存する。contact プロファイル置き場がある repo では、自分以外の参加者のプロファイルにリンクし、無ければ規約に従ってドラフト作成か `contact-profile-drafter` 等へ委譲。

## Step 4: 更新（規約にあるものだけ）

規約の承認レベルに従う。既定は「台帳・llms.txt は自動、決定ファイル・wiki は承認後」。規約に承認レベルの定めが無いものは、作成前に一覧を提示してユーザー確認する。

### 4-1. タスク台帳（自動）

台帳がある repo で、ガイドの規則どおりに直す。台帳が無い repo では何もしない。

1. **状態を直す**: 保存前の確認で承認された行だけ、ガイドの規則どおりに状態を直す（完了なら完了日を書いて完了節へ）。
2. **Issue の状態を写す**（ツールが GitHub Issue のときだけ）: closed は状態 `完了`・完了日 closedAt で完了節へ。open は Project の Status で `登録済み`／`進行中`、assignee で担当、Project の期限フィールドで期限を上書き（Project に無い Issue は `登録済み` のまま、担当・期限は Issue の値）。台帳に無い新規 Issue は出典 `Issue 直接 yyyy-mm-dd` で足す。`表のみ` の行とツール無し案件の行は写さない。
3. **今回の表の全行を進行中節に追記**: ID はガイドの振り方に従う（例: 台帳全体の通し番号 `T-<n>` なら、進行中・完了・archive を通じた最大値＋1 から順に振る）。既存の ID と重ならないことを確かめる。子は親列に親の ID。担当・期限は表の値。出典は `[yyyy-mm-dd 議事録](<相対パス>) 行 n`。状態はガイドの初期値（例 `未着手`。Issue を使うガイドでは `未登録`／`表のみ`）。再登場したタスクは既存行の担当・期限を直す。
4. 件数（追記 n・状態を直した n・完了へ移した n。Issue を使う repo では写した n・Issue 直接で足した n も）を Step 5 の報告に含める。

### 4-2. 決定ファイル（承認後）

議事録の「決定事項」を 1 件ずつ見て、規約の基準（例: 前提・定義・対象範囲・体制を変える決定だけ）で「ファイルにする重い決定か」を判定し、決定ごとに「重い／軽い ＋ 理由 1 文」で提示する。

- 重い決定は決定ファイルの案（規約の型。例: ADR の Context／Decision／Consequences／Alternatives Considered）と、wiki「主な決定」表に足す 1 行を見せる。`derived_from` に議事録のパス。
- 決定の一覧（llms.txt の Decisions 等）と突き合わせ、同じ決定が既にあれば「既存の決定ファイル `<パス>` の再確認」と伝えて新規にしない。内容が変わるなら既存を `status: superseded` にして新しいファイルを提案する。
- Issue コメント由来の決定は `（出典: Issue #n）` を付けて決定事項に載せ、同じ判定に乗せる。会議メモと食い違えば会議メモを採る。
- まだ決まっていないこと（「〜を確認してから決める」）は決定にせず、ネクストアクションか確認事項に置く。
- 重い決定が無ければ「今回はファイルにする決定なし（軽い決定 n 件は議事録に記載）」と伝える。
- 承認されたものだけ保存する。規約に判定基準が無い repo では、候補の一覧を提示してユーザーの振り分けに委ねる（候補の一つ一つを ADR にしない）。

### 4-3. llms.txt（自動）

規約が定める節（例: Recent Minutes に議事録の 1 行、Decisions に保存した決定の 1 行。Decisions は全件、Recent Minutes は直近 5 件程度）に追記する。定めが無ければ触らない。

### 4-4. wiki（承認後）

規約が定める範囲（例: 直近更新の 1 行を新しい順に先頭へ、前提・進行・未解決論点・用語の変化、主な決定表の 1 行、タスクのツール行の追加。進行表の行が空なら今回の内容から埋める案）を **変更前 → 変更後の差分の形で提示** し、承認されたものだけ反映する。承認前に書き換えない。候補を増やしすぎない。

規約に棚卸しの定めがあれば、台帳や wiki の各表のうち今回の議事録と矛盾する行と、規約の閾値（例: 90 日）以上更新の無い行を「棚卸し候補」として一覧で添える。候補を返すだけで消さない。

### 4-5. アクションの派生（台帳が無い repo）

横断タスクや相手別進行の正本（ボード・pipeline 等）が規約にあれば、その該当行の更新に留める。別のタスクファイルや外部 Issue を量産しない。作成前に一覧を提示してユーザー確認する。

## Step 5: 完了

1. 変更した文書の frontmatter とリンクを検証し、プロファイルに lint コマンドがあれば実行する。失敗したら直してから次へ。
2. 変更したファイルの一覧と件数を提示する（ネクストアクション 新規 n・未定 n／台帳 追記 n・状態の変更 n・完了 n／`status: done` にしたファイル。Issue を使う repo では 写し n・Issue 直接 n／下書き n／前回からの進捗 完了 n・更新 n・新規 n も）。
3. 元メモが drafts にある場合は、削除してよいか確認する（正式議事録に昇格済みのため）。
4. git 操作は、規約が議事録作成時のブランチ・コミット・push を定めているときだけ、その規約どおりに行う（例: 議事録・台帳・決定・llms.txt・wiki をまとめて 1 コミット。メッセージ案を提示して確認後に commit、規約があれば push・PR）。定めが無い repo では行わず、明示依頼のときだけ行う。
5. ツールが GitHub Issue の repo では、コミットのあとに起票することを案内する（規約が指す手段で）。議事録のパスと重要な未確認事項を短く報告する。

## 注意事項

- 規約は repo ごとに違う。**Step 0 を飛ばして特定構造を前提にしない。** 不明点は probe → 確認の順で潰す。
- 元メモは削除せず追記で充実させる。担当者・期限未定のアクションも「未定」で表に含める。
- 議事録の表は会議当日の記録。前回の議事録の表を書き換えない。状態は台帳（または規約の正本）だけが持つ。
- Issue・Project 側は読むだけ。close・再オープン・コメント投稿・本文やフィールドの編集は行わない。
- 派生ファイル（決定・wiki）は必ず人間レビューを経る。AI が勝手に確定しない。
