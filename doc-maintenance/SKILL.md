# doc-maintenance — 規約駆動のドキュメント点検スキル

文書は書いた時点では正しくても、元になったファイル（README・計画・定義）が後で変わると、数値や状態が古いまま残る。このスキルは、点検スクリプトで「古くなっていそうな文書」を機械的に一覧にし、1 件ずつ中身を確かめて、直す案を出してから直す。

点検スクリプトの正本は `scripts/check_docs.py`（標準ライブラリだけ。Python 3.11 以上）。各リポジトリには写しを置き、点検の対象は設定ファイル（既定は `scripts/check_docs.toml`）に書く。

## 絶対ルール

- **直す前に案を見せ、承認を取る。** 案はまとめて 1 回で見せる（1 件ずつ聞かない）。リンクの直しや一覧への追記のような機械的なものも、案の表に入れる。
- **外に出す文書（frontmatter の `audience: client` など、規約が共有物とする文書）は、変更の中身を見せてから直す。** 数値を数え直したときは、数え方と結果を案に書く。
- **本文は単体で読める形に直す。** 「〜に更新しました」「前は〜だった」のような経緯を本文に書かない（差分は git に残る）。
- **確かめて直さなかった文書にも、確かめた日を残す。** frontmatter の `reviewed: "YYYY-MM-DD"` を付けるか更新する。付けないと次の点検でまた出る。
- **規約が禁じることはしない。** 実データ・個人の値を文書に写さない、承認の要る操作は承認を待つ、など対象リポジトリの決まりに従う。
- 点検スクリプトの結果だけで直さない。必ず文書と、変わった元のファイルの差分を読んでから判断する。

## Step 0: 規約を読む（最初に必ず実行）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指す運用ガイドを読み、「ドキュメントの点検」の節から次を決める。

| 項目 | 既定（規約に無いとき） |
|---|---|
| 点検のコマンド | `python3 scripts/check_docs.py`（設定は `scripts/check_docs.toml`） |
| 点検する文書 | 設定の `targets`（中身が変わり続ける文書）と `link_targets`（リンクを見る文書） |
| 確かめ直しの手順 | 設定の `dated` の項目ごとに、規約に書かれた再確認の手順（無ければ「要確認」として残す） |
| 外に出す文書 | frontmatter の `audience: client`、または規約が共有物とする置き場 |
| git の運用 | 規約に従う。無ければコミットしない |

**節もスクリプトも無いリポジトリ**では、次を入れる案をまとめて 1 回で出し、承認後に入れる。

- `scripts/check_docs.py`：このスキルの `scripts/check_docs.py` の写し（先頭の docstring に正本の場所が書いてある）
- `scripts/check_docs.toml`：`references/config-example.toml` をもとに、そのリポジトリの置き場に合わせる。`targets` は中身が変わり続ける文書（README・運用ガイド・wiki・共有物・計画）だけにし、その時点の記録（議事録・メモ・決定）は入れない。例として書いたリンクは `ignore_links` で外す（`<slug>` や `{{...}}` を含む仮のリンクは書かなくても見ない）。一覧の照合でファイル名の末尾を外す（`.prompt.md` など）ときは `inventory` に `strip` を書く
- `AGENTS.md` の「ドキュメントの点検」の節：`references/agents-section.md` の雛形
- frontmatter の型に `reviewed` を足す（規約に frontmatter の型や lint があれば、そこにも足す）

## Step 1: 点検する

規約のコマンドで点検スクリプトを実行し、一覧を受け取る。見つかったものが無ければ、その旨を伝えて終える。

スクリプトを置けないリポジトリでは、同じ観点を手で見る（`git log -1 --format=%cI -- <file>` で文書と元のファイルの更新日を比べる、frontmatter の `status`・`related` を読む、本文の相対リンクの先があるかを見る）。

## Step 2: 1 件ずつ確かめて、対応を決める

| 見つかったもの | 確かめること | 対応の候補 |
|---|---|---|
| 元のファイルが後で更新された文書 | 文書の日付以降の元のファイルの差分（`git log -p --since=<文書の日付> -- <元のファイル>`）を読み、文書の数値・状態・手順・一覧に効くかを見る | 効くなら文書を直す。効かなければ `reviewed` だけ付ける |
| draft のまま日数が過ぎた文書 | まだ使っているか、置き換わったか | `active` にする、`superseded` にして置き換え先を `related` に書く、続けるなら `reviewed` を付ける（どれにするかは承認で決める） |
| related が置き換え済みの文書を指している | 置き換え先（新しい版）があるか | `related` を新しい版に替える |
| リンクの切れ | 移動・改名か（`git log --follow --diff-filter=R` やファイル名の検索で探す）、消えたか | 移った先に直す。消えていればリンクを外すか、言い換える |
| 日付の古い確認の記録 | 規約の再確認の手順（データの値の一覧の取り直し、突き合わせの notebook の再実行など） | 手順を実行できるなら実行して日付を更新する。データや権限が要ってできないなら、残りとして伝える |
| 一覧に載っていないファイル | 一覧の文書のどこに、どの型で載せるか | 一覧に行を足す。使わないファイルなら、置き場から外す案を出す |

## Step 3: 案をまとめて見せる

次の表で 1 回で見せ、承認を取る。外に出す文書は、変える文の前後を添える。

| ファイル | 見つかったこと | 直す案 | 確認が要る点 |
|---|---|---|---|

確かめた結果「直さない」ものも表に入れ、`reviewed` を付けることを書く。

## Step 4: 直して、点検し直す

承認されたものだけ直し、直した文書と確かめた文書の `reviewed` を今日の日付にする。点検スクリプトをもう一度実行し、残ったものは理由（データが要る、相手の確認待ち など）と一緒に伝える。

## Step 5: 記録する

規約の git の運用に従ってブランチ・コミット・PR を作る。コミットメッセージは規約の型に合わせ、点検で直したことが分かるようにする。

## いつ使うか

- 定期：規約に書かれた時期（例：月初）
- 文書を外に共有する前、リポジトリの構成や置き場を変えた後
