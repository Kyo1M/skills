# task-issue — 規約駆動のタスク起票スキル

タスクを GitHub Issue として起票し、Project（かんばん・ロードマップ）に載せるところまでを代行する。タスクの一覧と状態は対象リポジトリのタスク台帳が持ち、このスキルは台帳の `未登録` の行（入口は議事録の下書き・タスクファイル・自由記述）から Issue を作り、台帳の ID と状態を書き戻す側。コマンドの詳細は `references/gh-commands.md`。

## 絶対ルール

- **登録計画を見せて承認を得る前に、書き込み系のコマンド（`gh issue create`・`gh issue edit`・`gh project item-add`・`gh project item-edit`・GraphQL の mutation）を実行しない。** 読み取り（`gh issue list`・`gh issue view`・`gh project field-list`・GraphQL の query）は承認なしでよい。`gh issue` 系のコマンドには必ず `--repo <org>/<repo>` を付ける。
- 作成だけを扱う。作成後の親の付け替え・クローズ・期限の変更は GitHub の画面で行う（このスキルでは行わない）。
- Issue のタイトル・本文に生データ・個人情報・認証情報・実数値を書かない。議事録にそれらが混ざっていたら止めて伝える。
- 担当者が「止めて」と言ったらそこで止める。

## Step 0: 規約ディスカバリと先読み（承認不要）

ルートの `CLAUDE.md` / `AGENTS.md` と、そこが指す運用ガイド（例: `docs/guide/project-ops-guide.md`）を Read し、次を組み立てる。

| 項目 | 取得元 |
|---|---|
| タスク台帳 | 規約の台帳（例: `tasks/index.md`）。ID・状態の語彙、行を足す規則。台帳が無い repo では、規約が定める正本（議事録の表等）を読み、書き戻し先はユーザーに確認する |
| 議事録の置き場と「タスク登録の下書き」の型 | 規約（見出し＝アクション、本文の「出典:」「台帳:」「親:」「詳細:」行の意味） |
| タスクファイルの置き場と型 | 規約（例: `tasks/yyyymmdd_<slug>.md`。frontmatter `issue:`、「やること」の番号付き項目と `（#n）`） |
| タスクのツール | `docs/wiki/index.md`「進行」表の「タスクのツール」行。`GitHub Issue（リポジトリ: <org>/<repo>、Project: <URL>）` の形で登録先を読む。値が `なし（表のみ）` か `外部ボード` なら、Issue は作らず Step 5 の「貼れる文面」だけを出して終わる。行が無い・リポジトリが書かれていないときは、そこで聞く（wiki の行の追記案も出す） |
| メンバー | 同表の「メンバー」行（`名前: GitHub ID`）。担当を assignee に変換する。行が無い、または担当の名前が無いときは GitHub ID を聞き、追記案を出す（追記は承認後） |
| git 運用 | 規約が定めていれば、書き戻しのコミット案を出す |

続けて次を読む。

1. **`gh` が使えるか**: `gh auth status`。使えない（未導入・未ログイン）ときは「gh が無いので、貼れる文面を出します」と一度だけ伝え、Step 5 へ。Project を扱うには `project` スコープが要る（無ければ `gh auth refresh -s project` を案内）。
2. **Project のフィールド**（Project がある場合）: `references/gh-commands.md` 1 のクエリで、日付フィールド（開始日・期限に相当するもの）・`Status`・その他の単一選択フィールドの名前・ID・選択肢を取る。フィールド名は repo ごとに違うので固定しない。
3. **台帳**: 起票する行の ID（`yyyymmdd-#`）と状態。

## Step 1: 入口を判定する

引数と会話から次のどれかに決める。迷ったら 1 問で聞く。

| 入口 | 何を読むか | 何を起票するか |
|---|---|---|
| **(a) 議事録の下書き**（既定） | 直近の議事録（会議日が最新の 1 本）の「タスク登録の下書き」。指定があればそのファイル | `登録先: GitHub Issue` の行のうち、台帳の状態が `未登録` のもの（下書きの「台帳:」行の ID で引く）。登録先が空欄の行は「表のみ」として計画に載せない |
| **(b) タスクファイル** | 指定されたファイルの frontmatter（`issue:`）と「やること」の番号付き項目 | `issue:` があればその Issue を親に、無ければ親 Issue を新規に作り、「やること」の各項目を子として起票する。既に `（#n）` が付いた項目は飛ばす |
| **(c) 自由記述** | 会話の内容と、台帳に同じタスクの行（`未登録`）があればその行 | タイトル・担当・期限・親（あれば）を 1〜2 問で固めて起票する。台帳に行が無ければ、出典 `チャット yyyy-mm-dd` で行を足してから起票する。分量のある背景があるなら `task-breakdown` skill を先に勧める |

「計画だけ」と言われたときは、Step 2 で止まる。

## Step 2: 登録計画を作り、承認を取る

起票する 1 件を 1 行にした表を作る。列は 行・タイトル・担当（GitHub ID）・親・期限・開始日・（Project にある単一選択フィールドごとに 1 列）・備考。

```markdown
| 行 | タイトル | 担当（GitHub ID） | 親 | 期限 | 開始日 | 優先度 | 備考 |
|---|---|---|---|---|---|---|---|
| 4 | 対象範囲の定義をクライアントに確認する | pm-id | なし | 2026-09-30 | 2026-09-14 | 高 | |
| 4-1 | 前回提案書の対象範囲の記述を洗い出す | pm-id | 行 4 | 2026-09-16 | 2026-09-15 | 高 | |
| 7 | 中間報告の資料構成を決める | 未定 | #6 | 未定 → 2026-09-19（仮置き） | 2026-09-14 | 中 | 期限は「いつまでに決めるか」の仮置き |
```

- **タイトル**: 表の「アクション」そのまま。ID・番号は付けない（親子は GitHub の Parent issue で見る）。
- **担当**: 「メンバー」行で GitHub ID に変換する。`未定` は assignee なし。複数名は全員。
- **親**: 表の `#` 列から決める。`4-1` は同じ議事録の行 4（この実行で作る Issue）、`#6-1` は既存の Issue #6。入口 (b) は frontmatter の `issue:`（無ければ新規の親）。**既存の open Issue と同じ・似たタイトルの行があれば、`gh issue list --repo <org>/<repo> --state open --search "<語>"` で確かめ、「同じタスク（起票しない）／その Issue の子にする／別のタスク」を備考に書いて聞く。**
- **期限**: 表の値。`未定` の行はロードマップにバーが出ないので、「いつまでに決めるか」の日付を仮置きで提案し、備考に「仮置き」と書く。
- **開始日**: 親（議事録の行）は会議日、子は着手予定日（分からなければ会議日の翌営業日）。
- **単一選択フィールド**（Project にあるものだけ列を作る）: 議事録の議事内容・タスクファイルの記述から候補を入れる。決め手が無ければ空欄にして備考に「要指定」。
- **Status**: Project の既定（Todo）。列は作らない。

表を見せ、「この計画で起票してよいですか。直す行があれば行番号で教えてください」と 1 回で聞く。親の判断が要る行・要指定の欄がある場合も、この 1 回の質問にまとめる。「計画だけ」ならここで終わる。

## Step 3: 承認後に起票する

親 → 子の順に、1 件ずつ実行する（コマンドは `references/gh-commands.md` 2〜4）。

**Issue 本文の型**（議事録の行から作る親・単独の Issue）

```markdown
- 出典: [2026-09-14 議事録](https://github.com/<org>/<repo>/blob/main/docs/minutes/20260914_<slug>.md) 行 4
- 担当: <表示名>
- 期限: 2026-09-30
- 詳細: https://github.com/<org>/<repo>/blob/main/tasks/20260913_<slug>.md   ← 下書きに「詳細:」があるときだけ

<下書きの「概要」2〜3 行をそのまま>
```

- 出典・詳細のリンクは **`main` の blob URL に展開する**（Issue 画面では相対パスが解決されない）。
- 子 Issue の本文は「親: #n」と、下書きの概要（無ければアクションを 1〜2 行に膨らませたもの）だけ。出典は親が持つ。
- 入口 (b) の親を新規に作るときは、本文に「詳細: <タスクファイルの blob URL>」と、ファイルの「目的」節の要約 2〜3 行。
- 途中で失敗したら、そこまでに作った Issue の番号を示して止め、残りをどうするか聞く（作った Issue は消さない）。
- 既存の親 Issue（入口 (b) や `#6-1` の親）の本文に「詳細:」の行が無く、タスクファイルがあるときは、`gh issue edit <番号> --body` で本文の先頭の箇条書きに「詳細:」を 1 行足す（本文の他の部分は変えない）。これがこのスキルで唯一の既存 Issue への書き込み。

## Step 4: 書き戻し、結果を示す

1. **タスク台帳**（すべての入口）: 起票した行の ID を `#n`（別リポジトリなら `<短い名前>#n`）に、状態を `登録済み` に直す。親列が `yyyymmdd-#` のままなら、今回作った親の `#n` に直す。他の列は変えない。台帳に行が無かったタスク（入口 (c)、または (b) で新しく作った親・子）は、出典（`チャット yyyy-mm-dd`、またはタスクファイルの日付で `壁打ち yyyy-mm-dd`）・詳細・担当・期限を付けて進行中節に足す。議事録の表と「タスク登録の下書き」節はそのまま残す（書き換えない）。
2. **タスクファイル**（入口 (b)、または下書きに「詳細:」があった行）: frontmatter の `issue:` が空なら親の URL を入れ、「やること」の各項目の末尾に `（#n）` を付ける。
3. 結果を表で示す: 行 → Issue 番号（URL）→ 親 → Project に載ったか。
4. 規約に git 運用があれば、台帳とタスクファイルの書き戻しを 1 コミットにする案を示す（メッセージ案を提示して確認後に commit）。同じセッションで議事録の分をまだ push していなければ、同じブランチ・PR に含めてよい。

## Step 5: gh が無い・ツールが GitHub Issue でないとき（フォールバック）

Issue は作らず、下書きの 1 件ごとに「タイトル」と「本文」（出典・詳細は blob URL に展開済み）を貼れる形で出し、「貼ったら Issue 番号（またはカード名）を教えてください。台帳の ID と状態を直します」と伝える。番号を教えられたら Step 4 の書き戻しだけを行う（外部ボードは ID をそのままにして状態を `登録済み（カード名）` にする）。

## ルール

- 議事録・タスクファイル・会話に無い担当・期限・親を作らない。仮置きした期限は備考に「仮置き」と書く。
- 承認前に書き込み系のコマンドを実行しない。承認後も親 → 子の順に 1 件ずつ実行し、失敗したら止める。
- 出典・詳細のリンクは `main` の blob URL に展開する。
- 議事録の表は書き換えない。台帳は ID・状態（と親列の `yyyymmdd-#` → `#n`）だけを直す。進捗・完了は Project 側で持ち、台帳への写しは `meeting-minutes` skill が行う。
